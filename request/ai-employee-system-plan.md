# AI 社員システム 企画書

- 作成日: 2026-10-06（Asia/Tokyo）
- 状態: 初期企画・レビュー用。実装、モデル実行、既存会話ログの読取りは今回の対象外。
- 対象: Web 管理画面、MCP インターフェース、Codex CLI 実行基盤。
- 表記: **要望**は依頼内容、**提案**は本企画の設計判断、**確認済み**は参照資料または CLI help で確認した事項、**未検証**は実装前の検証事項を表す。
- 要望の出典: 本チャットの依頼内容。外部仕様の根拠は第14章に記載する。以下の設計は、明示的に「確認済み」とした部分を除き提案であり、既存実装の説明ではない。

## 1. 企画概要と業務課題

### 1.1 結論

**AI を単なるチャットではなく、組織・役割・継続セッションを持つ社員として管理する。** Web で組織と社員を構成し、管理 AI が作業を分解・委任し、作業 AI が自身のセッションで実行する。利用者は社員をクリックして、保存されている会話と実行履歴を追跡できる。

### 1.2 対象利用者・業務課題

- 対象利用者: 複数の AI に調査、設計、実装、レビューを分担させたいエンジニア。MVP は単一端末・単一運用者を想定する。
- 業務課題の仮説: セッション、担当、指示、モデル、実行結果が分散すると、誰に何を依頼し、どこまで完了したか追跡しにくい。導入前に利用者へ確認する。
- 業務目標: 「社員を選ぶ → 仕事を依頼する → 進捗と根拠を見る → 続きを依頼する」を一つの画面で完結させる。
- 失敗コスト: 誤ったセッションへの指示は文脈混入、二重実行は変更重複、無制限な委任は費用増加、過剰なログ公開は情報漏えいにつながる設計上のリスクとして扱う。

### 1.3 成功基準

- Web から社員、ペルソナ、モデル、作業ディレクトリを登録し、初回実行で得た実セッション ID と対応付けられる。
- 同じ社員への次の依頼が、選択された既存セッションへ送られる。セッション取り違え・同一セッションの同時実行を防ぐ。
- 管理 AI の依頼と作業 AI の結果を親子タスクとして追跡できる。
- 社員詳細から全セッションを選択でき、取得可能な全会話をページ送りで閲覧できる。欠落を完全な履歴として表示しない。
- 成功・失敗・承認待ち・停止・復旧を第12章の受入条件で判定できる。

### 1.4 実行制約と非目標

- 実行制約: 許可済み端末、作業ディレクトリ、モデル、CLI バージョン、認証状態の範囲で動作する。
- 非目標: MVP での複数クラウド実行基盤、給与・人事評価、モデル学習、完全自律の本番変更、他社製品対応。
- 非目標: 保存されていない会話や非公開の内部推論の復元、会話が常に全文モデル入力へ再投入されるという保証。
- 本文で示す技術スタック、制限値、保存期間は初期提案であり、採用済みではない。

## 3. 組織と社員モデル

### 3.1 組織構成

```text
人間の運用者
└── 開発部
    ├── 管理 AI: 開発マネージャー
    │   ├── 作業 AI: 調査担当
    │   ├── 作業 AI: 実装担当
    │   └── 作業 AI: レビュー担当
    └── 管理 AI: 運用マネージャー
        └── 作業 AI: 運用調査担当
```

- 組織単位と社員は別のデータとして保持する。社員は一つの主所属と、任意の一人の直属管理 AI を持つ。
- MVP の管理 AI は作業 AI にだけ委任する。管理 AI 間の再帰的委任、多重所属は後続段階とする。
- 組織ツリーと直属関係の循環を保存時に拒否する。異動で既存会話の閲覧権限が自動拡大しないよう再評価する。
- 社員削除ではなくアーカイブを標準とし、稼働中の社員は先に実行停止または完了を必要とする。

### 3.2 管理 AI と作業 AI の責任

| 種別 | 入力 | 責任 | 出力 | 境界 |
|---|---|---|---|---|
| 管理 AI | 目的、期限、範囲、完了条件 | 分解、担当提案、委任、成果物レビュー | 計画、子タスク、統合結果 | 人間の承認者を代行しない |
| 作業 AI | 明示された作業、許可範囲、完了条件 | 調査・実装・検証 | 結果、根拠、変更一覧、未解決事項 | 自分で権限や担当範囲を拡大しない |
| 業務サービス | 構造化された要求 | 権限検証、状態遷移、排他、予算制御 | 受付結果、実行 ID、監査記録 | LLM の文章ではなくコードで制御 |
| 人間 | 計画、変更内容、検証結果 | 承認、却下、優先順位、運用設定 | 承認記録、修正指示 | 高リスク操作の最終判断 |

### 3.3 自律・承認・禁止の境界

- 自律実行: 許可された情報の読取り、計画作成、割当済み作業、事前許可された開発環境内の変更・テスト。
- 人間の承認が必要: 新しい書込み範囲、外部への送信、本番操作、共有状態の変更、上限緩和、組織・権限変更。
- 禁止: 認証情報の表示・転送、禁止パスへのアクセス、未承認の破壊的操作、監査無効化、権限昇格、自己承認。
- ペルソナは行動指針であり認可機構ではない。認可は業務サービス、実行環境、MCP Gateway で強制する。
- 中継される会話、ログ、成果物はデータとして扱う。そこに含まれる命令で組織設定や実行権限を書き換えない。

## 4. Web 画面構成と利用フロー

| 画面 | 表示・操作 |
|---|---|
| ダッシュボード | 社員数、実行中、承認待ち、失敗、最近のタスク、ログ取込み異常 |
| 組織管理 | ツリー表示、部署追加、管理 AI / 作業 AI の配置、直属関係、社員選択 |
| 社員作成・編集 | 名前、役割、所属、基本ペルソナ、モデル、作業場所、許可ツール、制限 |
| 社員詳細 | 概要、会話、タスク、実行履歴、設定のタブ。既定は会話タブ |
| タスク詳細 | 目的、完了条件、親子関係、担当、状態、成果物、検証、再実行・停止 |
| 承認一覧 | 対象、操作範囲、理由、変更内容、期限、承認・却下 |
| 環境設定 | CLI、実行用 home、ログルート、モデル候補、同時実行数、保持方針、接続診断 |

### 4.1 社員を作成して仕事を依頼する

1. 組織画面で配置先を選び、社員種別と基本ペルソナを指定する。
2. モデル、作業ディレクトリ、ツール権限を選ぶ。作成だけではモデルを呼び出さない。
3. 「セッション初期化」を押すと、費用が発生し得る初回実行の内容を確認して開始する。
4. 初回の実セッション ID を保存し、社員に紐付ける。初期化用の指示・応答も履歴に残す。
5. 社員詳細から仕事を入力する。担当セッションと許可範囲を表示した上で実行する。

### 4.2 管理 AI に依頼する

1. 人間が管理 AI に目的と完了条件を渡す。
2. 管理 AI が担当候補と子タスクを提案する。MVP は委任前に人間が計画を承認する。
3. 承認済み子タスクだけを、許可された部下のセッションへ送る。
4. 作業 AI の結果を保存し、管理 AI の新しい実行に結果通知を渡す。通知待ちの間は CLI プロセスを占有しない。
5. 管理 AI が統合結果を作り、業務サービスが検証結果を添えて人間へ提示する。

### 4.3 社員の会話を確認する

- 組織上の社員をクリックすると、最新セッションを表示する。セッション一覧から過去の担当業務へ切り替える。
- ユーザー指示、AI 応答、公開されるツール入出力、時刻、実行 ID、エラーを時系列表示する。
- 「会話」「ツール実行」「監査イベント」を区別し、要約は原文の代替ではなく補助表示にする。
- 長い履歴はカーソルページングと仮想スクロールを使い、実行中の追記は SSE で配信する案とする。
- 再接続では最後に受信したイベント ID 以降を取得し、重複を排除する。

## 5. ペルソナ・モデル・セッション

### 5.1 基本ペルソナ

テンプレート候補は「管理」「調査」「実装」「レビュー」。次の項目を Web で編集できるようにする。

| 項目 | 内容 |
|---|---|
| role / objective | 担当職種と達成する目的 |
| responsibilities / non_goals | 担当範囲と実行しない業務 |
| communication_style | 応答言語、結論先行、報告の粒度 |
| output_contract | 結果、根拠、変更一覧、検証、未検証事項 |
| escalation_rules | 曖昧な要件、失敗、権限不足時の停止・確認条件 |
| persona_version | 編集履歴を追跡する不変の版番号 |

- ペルソナと権限ポリシーは別管理とする。自由入力のペルソナで権限を広げることはできない。
- 初回および後続の依頼には、選択された版と必要な役割情報を明示して渡す。CLI 固有の system message 注入機能を前提にしない。
- MVP ではセッション作成時のペルソナ版を固定する。変更を適用する場合は新しいセッションを作り、必要な文脈だけを明示的に引き継ぐ。

### 5.2 モデル設定

- 要望のモデル `gpt-6.1-sol` を初期候補として保持する。別モデルへ無断で置換しない。
- 候補一覧は管理者設定から始め、社員の既定モデルと実行時のモデルを区別して保存する。
- 確認済み: 公式 CLI reference に当該モデル名の例と `--model` がある。アカウントでの利用可否、料金、上限、実行成功は未検証。[S1][S2]
- 未検証のモデルにはその状態を表示する。利用不可なら失敗理由を提示し、自動フォールバックはしない。
- 同一セッション途中のモデル変更は PoC で挙動を検証するまで提供せず、新規セッションで変更する。

### 5.3 社員とセッションの関係

- 社員とセッションは `1:N`。一人の社員が担当業務ごとの会話履歴を持つ。
- 一つの実セッションは一人の社員だけに紐付ける。DB に一意制約を置く。
- `employee_id`、アプリ側 `session_id`、CLI 側 `codex_session_id` を混同しない。
- セッションの識別は実行端末と home の識別子を含めて管理し、外部文字列だけで所有者を判断しない。
- 既存セッションの紐付けは、許可されたログソースで存在・作業場所・識別子を確認し、履歴をプレビューして人間が確定する。
- ログしか存在しないセッションは閲覧専用にできる。ログを読めることと CLI で再開できることは別の能力として表示する。
- 明示的に選択したセッションのみ再開し、アプリの自動処理では `--last` を使用しない。

### 5.4 CLI 実行契約

確認済み: 非対話実行、JSONL 出力、ID 指定の再開、標準入力からのプロンプト読取りは公式資料とローカル help で確認できる。[S1][S2][S3]

```bash
# 初回実行。作業場所は Runner の検証済み cwd に設定する。
codex exec --model gpt-6.1-sol --json -

# 既存セッションへの追加作業。指示本文は標準入力に渡す。
codex exec --model gpt-6.1-sol --json resume <SESSION_ID> -
```

- 上記は呼出し形の例であり、今回実行していない。sandbox・承認設定を含む最終的な起動引数は PoC で固定する。
- Runner は shell 文字列を組み立てず、実行ファイルと引数配列を使う。自由入力を shell 展開させない。
- 初回の `thread.started` に含まれる `thread_id` を実 ID として保存する案とする。イベント例は公式資料で確認済みだが、端末上の発火・保存・再開の結合動作は未検証。[S1]
- ID の取得前はアプリ内の作成予約だけを保持する。初期化失敗時に仮 ID を再開可能な ID として表示しない。
- `thread.started` 取得後の異常終了では ID を保持して照合する。新規実行を無条件に繰り返してセッションを増殖させない。
- 各実行にモデル、CLI バージョン、ペルソナ版、cwd、ポリシー版、ID を保存し、後から設定変更で書き換えない。
- セッション永続化を必要とするため、通常フローでは `--ephemeral` を使わない。
- stdout はイベント、stderr は診断として別処理する。終了コードだけで業務上の完了を判定しない。

## 6. 会話ログと環境設定

### 6.1 設定項目

| 設定キー案 | 用途 | 検証・制約 |
|---|---|---|
| codex_binary_path | CLI 実行ファイル | 実在、実行可否、バージョン、管理者による変更 |
| execution_codex_home | 実行用 `CODEX_HOME` | 認証・設定・セッション領域への影響を診断し、稼働中は変更しない |
| log_source_roots | 既存 `.codex` 配下などの読取りルート | canonical path、読取り権限、許可範囲、対象ファイル形式 |
| workspace_roots | 社員の作業場所の候補 | 実行前の realpath 検証、禁止領域との交差拒否 |
| app_data_root | アプリ DB と正規化イベント | 読取りログとは分離し、アクセス制限する |
| model_allowlist | 選択可能モデル | 未検証・利用確認済み・無効の区分 |
| max_concurrent_runs | 全体の同時実行上限 | 初期案は2、同一セッションは常に1 |
| run_timeout_seconds | 実行上限時間 | 初期案は1800秒。超過は停止要求と監査 |
| retention_days | アプリ保持データの期間 | 初期案は90日。原本ログの削除とは別設定 |

- `log_source_roots` の変更は「読む場所の変更」であり、Codex のログ出力先変更ではない。
- `execution_codex_home` の変更は実行環境の変更として別操作にする。既存データの移動や認証コピーを自動実行しない。
- `.codex` の中を一括公開せず、確認済み parser に対応する会話ファイルだけを許可リストで読む。認証情報・環境変数の内容は画面へ返さない。
- ファイル構造、ローテーション、アーカイブ形式、イベント型、home 変更時の再開可否は PoC で検証する。特定の内部ファイル名や DB schema を安定 API と断定しない。
- 本企画作成では利用者の実会話ログや認証ファイルを読み取っていない。

### 6.2 取込み処理

1. ルートを canonical path に解決し、許可範囲と照合する。symlink による範囲外移動も拒否する。
2. parser の対応版を判定し、セッション一覧と取込み件数のプレビューを表示する。
3. 利用者が選択したセッションだけを索引化する。既存ログの全件自動取込みは既定で無効にする。
4. 新規実行は `--json` イベントを優先して収集し、既存会話ログは専用 adapter で正規化する。
5. 安定した source event ID がある場合はそれを使い、ない場合はファイル世代・オフセットなどで重複排除する。本文一致だけで正当な反復発言を削除しない。
6. 追記途中の不完全な行は保留し、末尾確定後に再読する。破損行は分離し、対象履歴を「一部欠落」と表示する。
7. 切詰め・ローテーション・原本消失を検知してチェックポイントを更新する。再索引時に原本を編集しない。

### 6.3 「会話全体」の定義

- 表示対象は「ソースに存在し、取込み権限があり、形式を解釈できる全イベント」。保存されなかった過去内容を生成して補完しない。
- API のイベント列とディスク上の会話が同じ完全性を持つとは仮定しない。出典と取得範囲を表示する。
- 取込み状態は `complete_for_source`、`partial`、`unsupported`、`missing` とし、全履歴の保証とは区別する。
- マスキング、原本欠落、未対応イベント、大きい出力の省略があれば位置と理由を明示する。
- システムが公開していない内部推論は表示対象外。公開された要約などがある場合も会話本文とは区別する。
- 「取得済み会話の全件表示」と「モデルが次回参照する文脈量」は別とし、コンテキスト圧縮の可能性を案内する。

## 7. システム構成

```text
Web Browser ── HTTP / SSE ── Web API ──────────┐
                                              ├── Application Service
MCP Client / 管理 AI ── MCP Server ────────────┘      ├── 組織・社員・セッション
                                                    ├── 認可・承認・予算
                                                    ├── Task / Run Queue
                                                    ├── DB / Audit / Events
                                                    └── Runner ── Codex CLI
Log Adapter ── 読取り専用ログソース ── 正規化イベント ───┘
```

- Web と MCP は別入口とするが、同じ認可・状態遷移・排他サービスを使用する。
- MCP Server は社員管理・タスク委任の入口であり、CLI の出力を単に横流しする仕組みにしない。
- Runner だけが CLI 起動権限を持つ。ブラウザと MCP クライアントには shell 実行機能を公開しない。
- ツール実行用の外部 MCP と、本製品が公開する社員管理 MCP を区別し、接続ごとに権限を管理する。
- 初期技術候補: TypeScript、React、Node.js、SQLite、SSE、DB を利用した永続キュー。採用は既存技術方針と PoC 後に決定する。
- MVP は localhost 限定でも認証、Origin 検証、CSRF 対策を持つ。ネットワーク公開と複数利用者は別のセキュリティ設計を必須とする。
- 分散実行へ進む場合は DB と queue の構成を再検討する。MVP から分散基盤を必須にしない。

## 8. Web API・MCP・LLM 契約

### 8.1 Web API 案

| API | 契約 |
|---|---|
| `POST /api/employees` | 名前、種別、所属、persona_version、model、workspace_id を受け、社員 ID を返す |
| `POST /api/employees/{id}/sessions` | 初期化予約と run_id を返す。実 ID 取得前に作成済みとしない |
| `POST /api/employees/{id}/session-bindings` | 選択済みソースとセッションを検証して紐付ける |
| `POST /api/tasks` | 目的、担当、完了条件、範囲、idempotency_key を受け、task_id を返す |
| `POST /api/sessions/{id}/messages` | prompt、期待する設定版、idempotency_key を受け、run_id を返す |
| `GET /api/sessions/{id}/events` | cursor と limit を受け、イベント、次 cursor、欠落状態を返す |
| `GET /api/runs/{id}/stream` | 権限検証後、SSE でイベントを返す |
| `POST /api/runs/{id}/cancel` | 停止要求を受理する。プロセス停止確認前に停止完了としない |
| `POST /api/approvals/{id}/decisions` | 人間の承認・却下と対象版を記録する |
| `POST /api/settings/log-sources/validate` | 管理者が指定した許可ルートの診断結果を返す |

### 8.2 MCP tools 案

共通 envelope は入力 schema で型を固定し、結果に `request_id`、`status`、`data`、`error` を持たせる。以下は本製品独自の提案名であり、既存 Codex tools の仕様ではない。

| Tool | 必須入力 | 出力 | 呼出し権限 |
|---|---|---|---|
| `employee_list` | scope_id | 閲覧可能な社員一覧 | 認証済みクライアント |
| `employee_get` | employee_id | 社員概要、実行状態 | 当該社員の閲覧権限 |
| `task_create` | employee_id、objective、acceptance_criteria、scope、idempotency_key | task_id、承認状態 | 許可された担当への依頼権限 |
| `task_delegate` | parent_task_id、worker_id、objective、acceptance_criteria、idempotency_key | child_task_id、run_id または承認待ち | 承認済み計画内の管理 AI |
| `task_get` | task_id | 状態、結果、根拠、未解決事項 | 当該タスクの閲覧権限 |
| `session_message` | employee_id、session_id、prompt、idempotency_key | run_id | 当該セッションの依頼権限 |
| `session_history` | session_id、limit | マスキング済みイベント、next_cursor、欠落状態 | 当該会話の閲覧権限 |
| `run_cancel` | run_id、reason | 停止要求の状態 | 人間または担当管理 AI |

- caller の ID と権限は認証済み接続から確定し、引数の `employee_id` を caller の本人証明に使わない。
- ページングの cursor は任意入力、limit は1〜200の初期案とする。自由なファイルパスや shell コマンドは tool 入力にしない。
- 管理 AI 向け MCP は、接続・run・employee に結び付いた短命な権限を使う。ユーザーの広い権限をそのまま渡さない。
- 管理 AI に社員権限変更、環境設定変更、人間の承認確定 tool を公開しない。

### 8.3 timeout・再試行・エラー隔離

- API / MCP の受付 timeout は初期案10秒。長時間実行は受付後に run_id で追跡し、接続を占有し続けない。
- 読取りは一時障害のみ最大2回再試行する案とする。書込みは同じ idempotency_key で受付結果を照会し、重複 side effect を防ぐ。
- idempotency_key は caller と操作種別でスコープ化し、同じキーで本文が違う要求は conflict とする。
- CLI 起動後の不明状態は自動再実行しない。外部への変更が起きていないことを確認できなければ人間へ照会する。
- エラーは `INVALID_INPUT`、`FORBIDDEN`、`SESSION_BUSY`、`MODEL_UNAVAILABLE`、`AUTH_REQUIRED`、`TIMEOUT`、`LOG_UNSUPPORTED`、`EXECUTION_UNKNOWN` に分類する案とする。
- 一人の失敗を他社員の実行失敗へ伝播させない。ただし依存する親タスクは待機または要確認に移す。

### 8.4 LLM 呼出し契約

| 呼出し | 入力 | 期待出力 | 拒否・停止条件 |
|---|---|---|---|
| セッション初期化 | ペルソナ、役割、許可範囲 | 役割確認、未確定事項 | 認証不良、ID 未取得、権限矛盾 |
| 管理 AI の計画 | 目的、社員一覧、範囲、上限 | 子タスク、担当、完了条件、依存関係 | 対象不明、循環、権限超過、予算超過 |
| 作業 AI の実行 | 作業、必要な文脈、許可ツール | 成果物、根拠、検証、未完了事項 | 要件不足、承認不足、実行制限超過 |
| 管理 AI の統合 | 各結果、検証記録、元の完了条件 | 統合結果と残課題 | 根拠欠落、相互矛盾、検証失敗 |

構造化出力は schema 検証後に採用する。LLM は分解・解釈・合成に用い、認可、ID 検証、排他、再試行、状態更新は通常コードで行う。

## 9. 業務パイプラインと状態制御

### 9.1 パイプライン

| 段階 | 開始条件 | 出力契約 | エラー処理 |
|---|---|---|---|
| 1. 入力収集 | 認証済み要求 | request_id、目的、担当、範囲 | 必須入力不足を拒否 |
| 2. 意図解釈 | schema が有効 | 目的、曖昧点、依頼種別 | 曖昧なら人間へ確認 |
| 3. コンテキスト検索 | 読取り権限あり | 出典付き文脈、取得範囲 | 欠落表示、無権限ソース除外 |
| 4. 計画生成 | 目的と文脈が確定 | 子タスク、完了条件、必要承認 | 制限超過や循環を拒否 |
| 5. ツール実行 | 承認・排他・予算を満たす | run_id、イベント、成果物 | timeout、停止、不明状態を記録 |
| 6. 結果検証 | 実行終了または成果物取得 | 受入条件別の pass / fail | 未検証を成功に変換しない |
| 7. 応答生成 | 検証結果あり | 結論、根拠、残課題、次の行動 | 根拠不足は限定的結果として報告 |
| 8. ログ・観測 | 全段階の追跡 ID あり | 監査、指標、再現情報 | 監査記録不能なら新規書込み実行を停止 |

ログは最後にだけ生成せず、各段階でも記録する。

### 9.2 状態

- Employee: `draft → ready ↔ disabled → archived`。実行中・失敗は Run から派生表示する。
- Session: `provisioning → ready → archived`。初期化失敗は `failed`、読取り専用は能力フラグで区別する。
- Task: `draft → awaiting_approval → queued → running → reviewing → completed`。
- Run: `queued → running → succeeded | failed | timed_out | cancelled | unknown`。停止要求中は `cancelling`。
- 必要な人間の判断は Approval と Task の状態で扱う。MVP は非対話 CLI の途中承認を Web から直接解決できると仮定しない。
- `succeeded` は CLI 実行成功、`completed` は業務の完了条件達成。両者を区別する。

### 9.3 排他・予算・停止

- 一つのセッションに対して同時 Run は1件。キュー受付とロック取得をトランザクション化する。
- 同じ作業場所への競合する書込みは直列化する。並列実装は分離した作業コピーを使い、統合は別承認とする。
- 初期案: 同時実行2件、親タスクの子タスク最大5件、委任深度1、検証で副作用なしと確認できた失敗の手動再実行最大1回。
- 金額や token 使用量を取得できない環境では「不明」と表示する。時間・実行数の制限は費用の厳密な上限保証ではない。
- Runner は heartbeat と所有権 token を保持する。再起動時は生存プロセスと所有権を照合し、期限切れだけで別実行を始めない。
- cancel はプロセス群の停止を試み、確認不能なら `unknown` とする。停止は外部変更の巻戻しではない。
- ロールバックは変更単位の逆操作または隔離作業コピーの破棄を、人間の確認後に行う。共有作業場所の強制 reset は行わない。

| Entity | 主な項目 |
|---|---|
| OrganizationUnit | id、parent_id、name、version |
| Employee | id、org_unit_id、manager_id、type、persona_version、default_model、policy_id |
| PersonaVersion | id、template_id、version、content、created_at |
| Session | id、employee_id、host_id、home_id、codex_session_id、capabilities、persona_version、workspace_id |
| Task | id、parent_task_id、employee_id、objective、acceptance_criteria、scope、status |
| Run | id、task_id、session_id、model、config_snapshot、status、exit_code、started_at、finished_at |
| ConversationEvent | id、session_id、run_id、source_id、sequence、kind、sanitized_payload、occurred_at |
| LogSource / Checkpoint | id、canonical_root、parser_version、file_generation、offset、coverage_state |
| Approval | id、action_digest、scope、requested_by、decided_by、expires_at、decision |
| AuditEvent | id、request_id、actor、action、target、result、reason、recorded_at |

- 永続状態: 社員、セッション対応、タスク、実行、設定版、承認、監査、マスキング済み会話。保持期間とアクセス権を明示する。

- キャッシュ: 一覧、検索索引、ダッシュボード集計。正本とせず、設定版・ソース世代変更時に無効化する。
- 長期記憶: セッション会話とは別機能とし、MVP では自動抽出・社員間共有を行わない。引継ぎ要約は出典付き成果物として扱う。
- 承認後に対象・操作・ペルソナ・権限版が変わった場合は承認を無効化する。期限切れ承認も再取得する。
- trace は `request_id → task_id → run_id → session_id → tool_call_id` で追跡する。
- 指標: queue 待ち時間、実行時間、モデル呼出し数、ツール呼出し数、失敗率、schema 検証失敗、承認介入数、取込み遅延。使用量は取得できた値だけを出す。

## 11. セキュリティと復旧方針

- raw log をブラウザに直接返さない。取込み前後とレスポンス境界でマスキングし、秘密情報を正規化 DB・検索索引・監査へ保存しない。
- マスキングは検出漏れがあり得るため、利用者が読取りソースを限定し、閲覧権限と保持期間でも露出を制限する。
- 表示 HTML は無害化し、ログ中の Markdown、URL、tool output を実行コードとして扱わない。
- 実行環境の認証情報は OS の保護領域または認証済み CLI に委ね、Web の設定取得 API や tool 結果に含めない。
- GUI から任意の環境変数・CLI 引数・MCP 接続先を無制限に設定できる設計にしない。
- 実行許可はプロンプトではなく強制可能な境界で与える。MVP で細かな承認を強制できない操作は提供しない。
- CLI に人間の対話承認が必要な場合は自動承認せず停止して報告する。Web 内承認と CLI の対話承認を同一機能とみなさない。
- CLI 異常終了: Run を失敗または不明として保存し、セッション ID と外部副作用を確認してから再試行する。
- ログ parser 異常: 対象ソースだけを隔離し、他ソースの取込みと既存閲覧を継続する。
- DB 復旧: アプリ DB のバックアップから復旧し、許可されたソースを再索引する。復旧だけでタスクを再実行しない。
- アプリのアーカイブは原本ログの削除ではない。物理削除・保持期間満了による削除は対象プレビューと人間の確認を伴う別操作とする。

| ID | シナリオ | 合格条件 |
|---|---|---|

| AC-02 | 初回セッション生成 | 実 ID 取得後にだけ ready となり、初期会話を表示できる |

| AC-11 | ログ破損・秘密情報 | 部分行を保留、破損を隔離し、秘密情報を画面・索引・監査へ露出しない |
| AC-12 | timeout・停止・再起動 | 生存プロセスを照合し、停止結果を区別して二重起動を防ぐ |
| AC-13 | ロールバック | 隔離作業で変更と逆操作を検証し、既存会話と監査を保持する |
| AC-14 | 設定変更と古い状態 | ペルソナ版変更で既存履歴を改変せず、失効した承認・キャッシュを利用しない |
| AC-15 | 会話中の偽命令 | ログに埋めた権限拡大・外部送信要求を制御命令として採用しない |

- unit: schema、権限、状態遷移、排他、重複抑止、マスキング、parser を匿名の合成 fixture で検証する。
- integration: fake CLI で正常、破損 JSONL、ID 未取得、異常終了、timeout を再現する。

- E2E: Web と MCP が同一認可を適用すること、社員選択から結果確認までの流れを確認する。
- 性能目標の初期案: 合成10万イベント、1ページ100件で履歴 API の p95 1秒以内。試験端末・索引条件を固定して測定し、実測前に達成済みとしない。
