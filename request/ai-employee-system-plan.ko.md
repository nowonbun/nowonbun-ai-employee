# AI 직원 시스템 기획서 — 한국어판

- 원본 작성일: 2026-10-06(Asia/Tokyo). 이 문서는 한국어판이며 원본의 당시 제안·미검증 상태를 유지한다.
- 당시 상태: 초기 기획·검토용. 당시 범위에는 구현, 모델 실행, 기존 대화 로그 열람이 포함되지 않았다. 현재 저장소의 구현 상태를 설명하는 문서는 아니다.
- 대상: 웹 관리 화면, MCP 인터페이스, Codex CLI 실행 기반.
- 표기: **요청**은 이용자 요구, **제안**은 설계 판단, **확인됨**은 당시 참조 자료 또는 CLI 도움말로 확인한 사항, **미검증**은 구현 전 검증할 사항이다.

## 1. 개요와 업무 문제

### 1.1 결론

AI를 단순한 채팅이 아니라 조직·역할·지속 세션을 가진 직원으로 관리한다. 웹에서 조직과 직원을 구성하고, 관리 AI가 작업을 분해·위임하며, 실무 AI는 자신의 세션에서 수행한다. 이용자는 직원을 선택해 저장된 대화와 실행 이력을 추적한다.

### 1.2 이용자와 문제

- 대상은 여러 AI에 조사·설계·구현·검토를 분담하려는 엔지니어다. MVP는 단일 기기·단일 운영자를 가정한다.
- 세션·담당·지시·모델·결과가 흩어지면 누가 무엇을 맡았고 어디까지 완료했는지 추적하기 어렵다는 문제 가설은 도입 전에 이용자에게 확인한다.
- 목표 흐름은 `직원 선택 → 업무 의뢰 → 진행 상황과 근거 확인 → 후속 의뢰`를 한 화면에서 마치는 것이다.
- 잘못된 세션에 지시하면 문맥이 섞이고, 중복 실행은 변경을 중복시키며, 무제한 위임은 비용을 늘리고, 과도한 로그 공개는 정보 노출을 일으킬 수 있다.

### 1.3 성공 기준

- 웹에서 직원·페르소나·모델·작업 디렉터리를 등록하고 첫 실행에서 얻은 실제 세션 ID와 연결한다.
- 동일 직원의 후속 요청을 선택한 기존 세션에 보내되, 세션 혼동과 동일 세션 동시 실행을 막는다.
- 관리 AI의 의뢰와 실무 AI의 결과를 부모·자식 Task로 추적한다.
- 직원 상세에서 모든 세션을 선택하고 접근 가능한 대화 전체를 페이지별로 볼 수 있다. 누락분을 완전한 기록으로 표시하지 않는다.
- 성공·실패·승인 대기·중단·복구는 12장의 인수 조건으로 판정한다.

### 1.4 제약과 비목표

- 허용된 기기, 작업 디렉터리, 모델, CLI 버전, 인증 상태 안에서 실행한다.
- MVP에서 다중 클라우드 실행, 급여·인사 평가, 모델 학습, 완전 자율 운영 배포, 타사 제품 지원은 목표가 아니다.
- 저장되지 않은 과거 대화나 비공개 내부 추론의 복원, 대화 전체의 차기 모델 입력 재투입은 보장하지 않는다.
- 이 문서의 기술 스택·제한값·보존 기간은 당시 초기 제안이며 채택 확정 사항이 아니다.

## 3. 조직과 직원 모델

### 3.1 조직 구성

```text
사람 운영자
└── 개발부
    ├── 관리 AI: 개발 매니저
    │   ├── 실무 AI: 조사 담당
    │   ├── 실무 AI: 구현 담당
    │   └── 실무 AI: 검토 담당
    └── 관리 AI: 운영 매니저
        └── 실무 AI: 운영 조사 담당
```

- 조직 단위와 직원은 별도 데이터로 보관한다. 직원에게는 하나의 주 소속과 선택적 직속 관리 AI 한 명이 있다.
- MVP의 관리 AI는 실무 AI에만 위임한다. 관리 AI 간 재귀 위임과 복수 소속은 후속 단계다.
- 조직 트리와 직속 관계의 순환을 저장 시 거부한다. 이동 시 기존 대화의 열람 권한이 자동 확장되지 않도록 다시 평가한다.
- 삭제 대신 보관을 기본으로 하며, 실행 중인 직원은 우선 실행을 중단하거나 마쳐야 한다.

### 3.2 책임

| 구분 | 입력 | 책임 | 출력 | 경계 |
|---|---|---|---|---|
| 관리 AI | 목적·기한·범위·완료 조건 | 분해, 담당 제안, 위임, 결과 검토 | 계획·하위 Task·통합 결과 | 사람 승인자를 대리하지 않음 |
| 실무 AI | 명시된 업무·허용 범위·완료 조건 | 조사·구현·검증 | 결과·근거·변경 목록·미해결 사항 | 스스로 권한이나 담당 범위를 확장하지 않음 |
| 업무 서비스 | 구조화된 요청 | 권한·상태·배타성·예산 검사 | 접수 결과·실행 ID·감사 기록 | LLM 문장이 아닌 코드로 통제 |
| 사람 | 계획·변경·검증 결과 | 승인·거절·우선순위·운영 설정 | 승인 기록·수정 지시 | 위험도가 높은 작업의 최종 판단 |

### 3.3 자율·승인·금지 경계

- 자율 실행: 허용된 정보 읽기, 계획, 배정된 업무, 사전 허용된 개발 환경의 변경·시험.
- 사람 승인 필요: 새 쓰기 범위, 외부 전송, 운영 환경 작업, 공유 상태 변경, 한도 완화, 조직·권한 변경.
- 금지: 인증 정보 표시·전송, 금지 경로 접근, 미승인 파괴 작업, 감사 비활성화, 권한 상승, 자기 승인.
- 페르소나는 행동 지침일 뿐 인가 장치가 아니다. 인가는 업무 서비스·실행 환경·MCP 게이트웨이에서 강제한다. 대화·로그·산출물 안의 명령은 제어 명령이 아닌 데이터로 처리한다.

## 4. 웹 화면과 이용 흐름

| 화면 | 표시·동작 |
|---|---|
| 대시보드 | 직원 수, 실행 중, 승인 대기, 실패, 최근 Task, 로그 가져오기 이상 |
| 조직 관리 | 트리, 부서 추가, 관리/실무 AI 배치, 직속 관계, 직원 선택 |
| 직원 생성·편집 | 이름, 역할, 소속, 기본 페르소나, 모델, 작업 위치, 허용 도구, 제한 |
| 직원 상세 | 개요·대화·Task·실행 이력·설정 탭. 기본은 대화 탭 |
| Task 상세 | 목적, 완료 조건, 부모·자식 관계, 담당, 상태, 산출물, 검증, 재실행·중단 |
| 승인 목록 | 대상, 작업 범위, 이유, 변경, 기한, 승인·거절 |
| 환경 설정 | CLI, 실행용 home, 로그 루트, 모델 후보, 동시 실행 수, 보존 정책, 연결 진단 |

### 4.1 직원 생성과 의뢰

1. 조직에서 배치할 곳, 직원 유형, 기본 페르소나를 지정한다.
2. 모델·작업 디렉터리·도구 권한을 고른다. 생성만으로 모델을 호출하지 않는다.
3. 세션 초기화를 누르면 비용이 발생할 수 있는 첫 실행 내용을 확인하고 시작한다.
4. 실제 세션 ID를 받아 직원에 연결하고 초기 지시와 응답도 기록한다.
5. 직원 상세에서 담당 세션·허용 범위를 확인한 후 업무를 입력한다.

### 4.2 관리 AI에 의뢰

1. 사람이 관리 AI에 목적과 완료 조건을 전달한다.
2. 관리 AI가 담당 후보와 하위 Task를 제안한다. MVP에서는 위임 전에 사람이 계획을 승인한다.
3. 승인된 Task만 허용된 부하 직원의 세션으로 보낸다.
4. 실무 AI 결과를 저장하고 관리 AI의 새 실행으로 결과 알림을 전달한다. 알림 대기 중 CLI 프로세스를 점유하지 않는다.
5. 관리 AI가 통합하고 업무 서비스가 검증 결과와 함께 사람에게 제시한다.

### 4.3 대화 확인

- 직원을 선택하면 최신 세션을 표시하고 세션 목록에서 과거 업무로 전환한다.
- 사용자 지시·AI 응답·공개 도구 입출력·시각·실행 ID·오류를 시간순으로 표시한다.
- 대화·도구 실행·감사 이벤트를 구분한다. 요약은 원문의 대체물이 아니다.
- 긴 이력은 커서 페이지네이션과 가상 스크롤, 실행 중 추가 이벤트는 SSE를 제안한다. 재연결 시 마지막 이벤트 이후를 읽고 중복을 제거한다.

## 5. 페르소나·모델·세션

### 5.1 기본 페르소나

후보 템플릿은 관리·조사·구현·검토다. 웹에서 `role / objective`(직무·목적), `responsibilities / non_goals`(책임·비목표), `communication_style`(언어·보고 방식), `output_contract`(결과·근거·변경·검증·미검증), `escalation_rules`(중단·확인), `persona_version`(불변 버전)을 편집한다. 페르소나와 인가 정책은 분리한다. 첫 실행 및 후속 의뢰에 선택한 버전과 역할을 명시하되 CLI 전용 system message 삽입을 가정하지 않는다. 이 초기 기획의 MVP 제안은 세션의 페르소나 버전을 고정하고 변경 시 새 세션에 필요한 문맥만 명시적으로 넘기는 것이다.

### 5.2 모델

- 요청 모델 `gpt-6.1-sol`을 초기 후보로 유지하고 임의로 다른 모델로 바꾸지 않는다.
- 관리자가 후보를 설정하고 직원의 기본 모델과 실행 모델을 구분해 저장한다.
- 당시 공식 CLI 참조에서 해당 모델명 예시와 `--model`을 확인했으나 계정 이용 가능 여부·요금·한도·실행 성공은 미검증이다.[S1][S2]
- 사용 불가 시 이유를 제시하고 자동 대체하지 않는다. 동일 세션 중간의 모델 변경은 PoC 전에는 제공하지 않는다는 당시 제안이다.

### 5.3 직원과 세션

- 직원:세션은 `1:N`; 실제 세션 하나는 직원 한 명에게만 연결하고 DB에서 유일성을 보장한다.
- `employee_id`, 앱의 `session_id`, CLI의 `codex_session_id`는 다르다. 호스트와 home 식별자도 함께 관리한다.
- 기존 세션은 허용된 로그 소스에서 존재·작업 위치·식별자를 확인하고 미리보기를 거쳐 사람이 확정한다. 로그만 있는 세션은 읽기 전용일 수 있다.
- 명시적으로 선택한 세션만 재개하고 앱의 자동 처리에 `--last`를 사용하지 않는다.

### 5.4 CLI 실행 계약

당시 공식 자료와 로컬 도움말에서 비대화형 실행, JSONL, ID 지정 재개, 표준 입력 프롬프트를 확인했다.[S1][S2][S3]

```bash
# 첫 실행: Runner가 검증한 cwd 사용
codex exec --model gpt-6.1-sol --json -

# 기존 세션에 후속 업무: 지시문은 표준 입력으로 전달
codex exec --model gpt-6.1-sol --json resume <SESSION_ID> -
```

- 위 명령은 호출 형태의 예시이고 당시 실행하지 않았다. sandbox·승인 관련 인자는 PoC에서 정한다.
- Runner는 셸 문자열이 아니라 실행 파일과 인자 배열을 사용한다. 첫 `thread.started`의 `thread_id`를 실제 ID로 저장하는 것은 당시 제안이며 실제 결합 동작은 미검증이다.
- ID를 얻기 전에는 생성 예약만 유지하고 가짜 ID를 재개 가능하다고 표시하지 않는다. ID 취득 뒤 비정상 종료하면 기존 ID를 대조한 후 처리한다.
- 각 실행의 모델·CLI 버전·페르소나 버전·cwd·정책 버전·ID를 기록하고 이후 설정 변경으로 과거 이력을 덮어쓰지 않는다.
- 세션 지속을 위해 일반 흐름에서 `--ephemeral`을 사용하지 않는다. stdout 이벤트와 stderr 진단을 분리하며 종료 코드만으로 업무 완료를 판단하지 않는다.

| `workspace_roots` | 직원 작업 위치 후보 | 실행 전 realpath 검사, 금지 영역 교차 거부 |
| `app_data_root` | 앱 DB와 정규화 이벤트 | 읽기 로그와 분리, 접근 제한 |
| `model_allowlist` | 선택 모델 | 미검증·사용 확인·비활성 구분 |
| `max_concurrent_runs` | 전체 동시 실행 | 초기안 2, 동일 세션은 항상 1 |
| `run_timeout_seconds` | 실행 제한 시간 | 초기안 1800초, 초과 시 중단 요청·감사 |
| `retention_days` | 앱 데이터 보존 | 초기안 90일, 원본 로그 삭제와 별개 |

- 로그 소스 변경은 읽을 곳의 변경이며 Codex 로그 출력 위치 변경이 아니다. 실행용 home 변경은 별도 작업이고 데이터·인증을 자동 복사하지 않는다.
- `.codex` 전체를 공개하지 않고 지원 parser의 대화 파일만 허용 목록으로 읽는다. 인증 정보·환경 변수 내용은 화면에 반환하지 않는다.
- 내부 파일 구조·회전·보관 형식·이벤트 유형·home 변경 후 재개 가능 여부는 PoC 대상이다. 이 기획 당시 실제 대화·인증 파일은 읽지 않았다.

### 6.1 가져오기

1. 루트를 실제 경로로 풀고 허용 범위 및 심볼릭 링크 이탈을 검사한다.
2. parser 버전을 판별하고 세션·건수 미리보기를 표시한다.
3. 사용자가 선택한 세션만 색인한다. 전체 자동 가져오기는 기본 비활성화한다.
4. 신규 실행은 `--json` 이벤트, 기존 로그는 전용 어댑터로 정규화한다.
5. 안정적인 원본 이벤트 ID가 있으면 사용하고, 없으면 파일 세대·오프셋으로 중복 제거한다. 본문 일치만으로 반복 발언을 삭제하지 않는다.
6. 작성 중인 불완전 행은 보류하고 손상 행은 격리해 일부 누락을 표시한다.
7. 잘림·회전·원본 소실을 감지하고 체크포인트를 갱신하되 원본은 편집하지 않는다.

### 6.2 ‘대화 전체’의 범위

표시 범위는 원본에 존재하고 접근 권한이 있으며 해석 가능한 모든 이벤트다. 저장되지 않은 과거를 만들어 채우지 않는다. API 이벤트와 디스크 대화가 동일하게 완전하다고 가정하지 않으며 출처와 수집 범위를 보인다. 상태는 `complete_for_source`, `partial`, `unsupported`, `missing`으로 구분한다. 마스킹·원본 누락·미지원 이벤트·대형 출력 생략은 위치와 이유를 명시한다. 비공개 내부 추론은 대상이 아니고, 공개된 요약도 대화 본문과 구분한다. 기록의 전체 표시와 모델의 다음 문맥 입력량은 별개다.

## 7. 시스템 구성

```text
웹 브라우저 ── HTTP / SSE ── Web API ───────────┐
                                               ├── 애플리케이션 서비스
MCP 클라이언트 / 관리 AI ── MCP 서버 ───────────┘    ├── 조직·직원·Task·승인
                                                   ├── 정책·권한·상태·대기열
                                                   ├── Runner → Codex CLI
                                                   ├── 로그 가져오기 어댑터
                                                   └── DB·감사·이벤트
```

- Web과 MCP는 같은 업무 서비스를 사용하고 인가를 공유한다. Runner는 장시간 실행과 프로세스 소유권을 관리한다.
- 당시 React / Node.js / SQLite는 제안일 뿐 확정이 아니다. localhost MVP라도 인증·Origin·CSRF 대책이 필요하며 외부 공개·다중 이용자·분산 실행은 별도 설계 대상으로 둔다.

## 8. Web API·MCP·LLM 계약

### 8.1 Web API 제안

| API | 계약 |
|---|---|
| `POST /api/employees` | 이름·유형·소속·페르소나 버전·모델·작업 공간 ID를 받아 직원 ID 반환 |
| `POST /api/employees/{id}/sessions` | 초기화 예약과 Run ID 반환. 실제 ID 전에는 생성 완료 아님 |
| `POST /api/employees/{id}/session-bindings` | 선택한 소스와 세션을 검증해 연결 |
| `POST /api/tasks` | 목적·담당·완료 조건·범위·멱등 키를 받아 Task ID 반환 |
| `POST /api/sessions/{id}/messages` | 프롬프트·예상 설정 버전·멱등 키를 받아 Run ID 반환 |
| `GET /api/sessions/{id}/events` | cursor·limit에 따라 이벤트·다음 cursor·누락 상태 반환 |
| `GET /api/runs/{id}/stream` | 권한 검증 후 SSE 이벤트 제공 |
| `POST /api/runs/{id}/cancel` | 중단 요청 접수. 프로세스 종료 확인 전 완료 처리 금지 |
| `POST /api/approvals/{id}/decisions` | 사람의 승인·거절 및 대상 버전 기록 |
| `POST /api/settings/log-sources/validate` | 관리자 지정 루트 진단 |

### 8.2 MCP 도구 제안

공통 결과는 `request_id`, `status`, `data`, `error`를 가진다. 다음 명칭은 이 제품 고유의 제안이고 기존 Codex 도구 명세가 아니다.

| 도구 | 필수 입력 | 출력 | 권한 |
|---|---|---|---|
| `employee_list` | `scope_id` | 열람 가능한 직원 | 인증된 클라이언트 |
| `employee_get` | `employee_id` | 직원 개요·실행 상태 | 해당 직원 열람 권한 |
| `task_create` | `employee_id`, `objective`, `acceptance_criteria`, `scope`, `idempotency_key` | Task ID·승인 상태 | 허용된 의뢰 권한 |
| `task_delegate` | `parent_task_id`, `worker_id`, `objective`, `acceptance_criteria`, `idempotency_key` | 하위 Task ID·Run ID 또는 승인 대기 | 승인된 계획 내 관리 AI |
| `task_get` | `task_id` | 상태·결과·근거·미해결 | 해당 Task 열람 권한 |
| `session_message` | `employee_id`, `session_id`, `prompt`, `idempotency_key` | Run ID | 해당 세션 의뢰 권한 |
| `session_history` | `session_id`, `limit` | 마스킹된 이벤트·다음 cursor·누락 상태 | 해당 대화 열람 권한 |
| `run_cancel` | `run_id`, `reason` | 중단 요청 상태 | 사람 또는 담당 관리 AI |

- 호출자 신원은 인증된 연결에서 확정한다. 인자의 `employee_id`를 본인 증명으로 사용하지 않는다.
- cursor는 선택 입력이고 limit 1~200은 초기안이다. 임의 파일 경로나 셸 명령을 도구 입력으로 받지 않는다.
- 관리 AI에는 연결·Run·직원에 묶인 단기 권한만 준다. 직원 권한·환경 설정 변경이나 사람 승인 확정 도구는 노출하지 않는다.

### 8.3 시간 초과·재시도·오류 격리

- API/MCP 접수 시간 제한 초기안은 10초다. 장시간 실행은 접수 후 Run ID로 추적한다.
- 읽기는 일시 장애에 한해 최대 2회 재시도를 제안한다. 쓰기는 같은 멱등 키의 접수 결과를 조회해 중복 효과를 막는다. 같은 키로 다른 본문을 보내면 충돌이다.
- CLI 시작 뒤 결과가 불명확하면 자동 재실행하지 않는다. 외부 변경 여부를 확인하지 못하면 사람에게 묻는다.
- 오류 후보: `INVALID_INPUT`, `FORBIDDEN`, `SESSION_BUSY`, `MODEL_UNAVAILABLE`, `AUTH_REQUIRED`, `TIMEOUT`, `LOG_UNSUPPORTED`, `EXECUTION_UNKNOWN`.
- 직원 한 명의 실패를 타 직원에게 전파하지 않되 의존 부모 Task는 대기·확인 필요로 둔다.

### 8.4 LLM 호출

| 호출 | 입력 | 기대 출력 | 거부·중단 |
|---|---|---|---|
| 세션 초기화 | 페르소나·역할·허용 범위 | 역할 확인·미확정 사항 | 인증 오류·ID 미취득·권한 충돌 |
| 관리 AI 계획 | 목적·직원 목록·범위·한도 | 하위 Task·담당·완료 조건·의존 관계 | 대상 불명·순환·권한/예산 초과 |
| 실무 AI 실행 | 업무·필요 문맥·허용 도구 | 산출물·근거·검증·미완료 | 요건/승인 부족·실행 한도 초과 |
| 관리 AI 통합 | 각 결과·검증·원래 완료 조건 | 통합 결과·잔여 과제 | 근거 부족·모순·검증 실패 |

구조화 출력은 schema 검증 후 채택한다. LLM은 분해·해석·종합에 쓰되, 인가·ID·배타성·재시도·상태 갱신은 코드로 처리한다.

## 9. 업무 파이프라인과 상태

| 단계 | 시작 조건 | 출력 | 오류 처리 |
|---|---|---|---|
| 1. 입력 수집 | 인증된 요청 | 요청 ID·목적·담당·범위 | 필수 입력 부족 거부 |
| 2. 의도 해석 | 유효한 schema | 목적·모호점·요청 유형 | 모호하면 사람에게 확인 |
| 3. 문맥 검색 | 읽기 권한 | 출처가 있는 문맥·수집 범위 | 누락 표시·무권한 소스 제외 |
| 4. 계획 생성 | 목적·문맥 확정 | 하위 Task·완료 조건·승인 | 한도 초과·순환 거부 |
| 5. 도구 실행 | 승인·배타성·예산 충족 | Run ID·이벤트·산출물 | 시간 초과·중단·불명 상태 기록 |
| 6. 결과 검증 | 실행 종료 또는 산출물 | 조건별 pass / fail | 미검증을 성공으로 바꾸지 않음 |
| 7. 응답 | 검증 결과 | 결론·근거·잔여 과제·다음 행동 | 근거 부족 시 제한된 결과 |
| 8. 기록·관측 | 전체 추적 ID | 감사·지표·재현 정보 | 감사 기록 불능 시 신규 쓰기 중단 |

기록은 마지막에만 생성하지 않고 각 단계에서 남긴다.

- Employee: `draft → ready ↔ disabled → archived`. 실행 중·실패는 Run으로부터 표시한다.
- Session: `provisioning → ready → archived`; 초기화 실패는 `failed`, 읽기 전용은 능력 플래그다.
- Task: `draft → awaiting_approval → queued → running → reviewing → completed`.
- Run: `queued → running → succeeded | failed | timed_out | cancelled | unknown`; 중단 요청 중 `cancelling`.
- 사람 판단은 Approval과 Task 상태로 처리한다. CLI 성공(`succeeded`)과 업무 완료(`completed`)는 다르다.
- 세션당 동시 Run은 1개이며 대기열 접수·잠금 획득을 트랜잭션으로 처리한다. 동일 작업 위치의 충돌 쓰기는 직렬화한다.
- 초기안: 전체 동시 2개, 부모당 자식 5개, 위임 깊이 1, 부작용 없음이 확인된 실패의 수동 재실행 1회.
- 사용량을 얻지 못하면 비용을 ‘알 수 없음’으로 표시한다. 시간·횟수 제한은 정확한 비용 상한 보장이 아니다.
- Runner는 heartbeat·소유권 token을 관리한다. 재시작 시 살아 있는 프로세스와 대조하고 기한 만료만으로 새 실행을 시작하지 않는다.
- 취소 결과를 확인할 수 없으면 `unknown`이다. 중단은 외부 변경을 되돌리지 않는다. 롤백은 사람 확인 후 변경별 역작업이나 격리 사본 폐기로 처리하고 공유 작업 위치를 강제 reset하지 않는다.

- 영속 상태는 직원·세션 연결·Task·Run·설정 버전·승인·감사·마스킹된 대화다. 보존 기간과 권한을 명시한다.
- 실행 스트림 버퍼·불완전 행·단기 token은 임시 상태이며 종료 또는 만료 시 폐기한다.
- 목록·검색 인덱스·집계는 캐시이고 정본이 아니다. 설정 버전·소스 세대 변경 시 무효화한다.
- 장기 기억은 세션 대화와 별도 기능이며 MVP에서는 자동 추출·직원 간 공유를 하지 않는다. 인계 요약에는 출처가 있어야 한다.
- 승인 후 대상·작업·페르소나·권한 버전이 달라지면 승인을 무효화한다. 추적 체계는 `request_id → task_id → run_id → session_id → tool_call_id`다.
- 지표는 대기 시간, 실행 시간, 모델/도구 호출 수, 실패율, schema 오류, 승인 개입, 가져오기 지연이다. 사용량은 실제 얻은 값만 표시한다.

## 11. 보안과 복구

- 원본 로그를 브라우저에 그대로 반환하지 않는다. 가져오기·응답 경계에서 마스킹하고 비밀 정보를 DB·색인·감사에 저장하지 않는다. 탐지 누락 가능성은 소스 제한·열람 권한·보존 기간으로도 줄인다.
- 표시 HTML을 무해화하고 로그 안의 Markdown·URL·도구 출력을 실행 코드로 취급하지 않는다.
- 인증 정보는 OS 보호 영역이나 인증된 CLI에 맡기고 Web API·도구 응답으로 내보내지 않는다. GUI에서 임의 환경 변수·CLI 인자·MCP 연결을 무제한 설정할 수 없게 한다.
- 실행 권한은 프롬프트가 아닌 강제 가능한 경계에 둔다. CLI가 사람의 대화형 승인을 요구하면 자동 승인하지 않고 중단·보고한다.
- CLI 비정상 종료 시 실패 또는 불명으로 저장하고 세션 ID·외부 효과를 대조한 후 재시도한다.
- 로그 parser 오류는 해당 소스만 격리한다. DB는 백업에서 복원한 뒤 허용 소스를 재색인하되 복원만으로 Task를 다시 실행하지 않는다.
- 앱 보관과 원본 로그 삭제는 별개다. 물리 삭제에는 대상 미리보기와 사람 확인이 필요하다.

아래 조건은 미래 구현의 인수 기준이며 이 문서만으로 통과가 입증되지는 않는다.

|---|---|---|
| AC-01 | 웹에서 직원 생성 | 필수값 검사, 페르소나·모델·소속 저장 |
| AC-02 | 첫 세션 생성 | 실제 ID 후에만 ready, 초기 대화 표시 |
| AC-03 | 같은 직원 후속 업무 | 같은 실제 세션 ID로 재개, 같은 대화에 이벤트 추가 |
| AC-04 | 기존 세션 연결 | 소유자·소스·작업 위치 확인, 중복 연결 거부 |
| AC-05 | 관리 AI 위임 | 승인된 담당에게만 하위 Task, 결과를 부모로 반환 |
| AC-06 | 직원의 전체 대화 | 여러 페이지의 접근 가능한 이벤트와 누락 위치 표시 |
| AC-07 | 로그 루트 변경 | 이전 원본 변경 없이 새 루트 진단·가져오기 |
| AC-08 | 동시·중복 요청 | 동일 키 재전송 시 증식 없음, 세션당 동시 Run 없음 |
| AC-09 | 모델 불가·인증 만료 | 이유 표시, 임의 대체나 무한 재시도 없음 |
| AC-10 | 승인·인가 위반 | 자기 승인·범위 초과·만료 승인 거부·감사 |
| AC-11 | 로그 손상·비밀 | 부분 행 보류·손상 격리·비밀 비노출 |
| AC-12 | 시간 초과·중단·재시작 | 생존 프로세스 대조·중단 결과 구분·중복 실행 방지 |
| AC-13 | 롤백 | 격리된 변경·역작업 검증, 대화·감사 유지 |
| AC-14 | 설정 변경·오래된 상태 | 기존 이력 불변, 실효 승인·캐시 재사용 금지 |
| AC-15 | 대화의 위조 명령 | 권한 확대·외부 전송 지시를 제어 명령으로 채택하지 않음 |

- 단위 시험은 schema·권한·상태·배타성·중복·마스킹·parser를 익명 합성 fixture로 검증한다.
- 통합 시험은 가짜 CLI로 정상·손상 JSONL·ID 미취득·비정상 종료·시간 초과를 재현한다.
- 실제 CLI PoC는 사람이 허용한 격리 환경에서 첫 생성·재개·영속화를 확인하며 비용 발생 가능성 때문에 별도 승인한다.
- E2E는 Web/MCP의 동일 인가와 직원 선택부터 결과 확인까지 검증한다.
- 성능 초기안은 합성 이벤트 10만 건, 페이지당 100건, 이력 API p95 1초 이내다. 환경·색인 조건을 고정해 측정 전에는 달성으로 표시하지 않는다.

## 13. 구현 단계와 미결 사항

| 단계 | 산출물 | 다음 단계 조건 |
|---|---|---|
| Phase 0: 기술 검증 | CLI 어댑터·익명 로그 fixture·권한 시험 | 첫 생성·재개·이력·강제 경계 확인 |
| Phase 1: 직원과 대화 | 웹 직원·조직·설정·대화·단일 Run | 관련 AC-01~04, 06~09, 11, 12, 14 확인 |
| Phase 2: 조직적 실행 | 관리/실무 AI·승인·MCP·부모/자식 Task | 전체 MVP 인수 조건 확인 |
| Phase 3: 운영 확장 | 검색·사용량·알림·다중 이용자·분산 실행 검토 | 이용 실적과 보안 요건으로 채택 결정 |

MVP는 Phase 2까지다. 기술 검증과 스택 결정 후 일정과 공수를 산정한다.

| 쟁점 | 당시 초기안 | 확인이 필요한 이유 |
|---|---|---|
| 이용 형태 | 로컬·단일 운영자 | 공개 범위에 따라 인증·데이터 분리 변경 |
| 스택 | React / Node.js / SQLite | 당시 프로젝트 방침 미지정 |
| 직원·세션 | 직원 1:N, 실제 세션 공유 금지 | 대화·권한 혼합 방지 |
| 관리 AI 위임 | 계획 승인 후 실무 AI에 위임 | 자율 위임 범위 결정 필요 |
| 실행용 home | 로그 읽기와 분리해 명시 설정 | 인증 공유·재개·설정 충돌 미검증 |
| 로그 형식 | 버전별 어댑터 | 실제 로컬 데이터의 형식·완전성 미검증 |
| CLI 승인 | 최소 권한·비대화형 허용 작업 | Web의 실행 중 승인 연계 미검증 |
| 모델 | `gpt-6.1-sol` 후보 유지 | 계정 실행·요금 미검증 |
| 보존·비용 | 90일, 시간·횟수 제한 | 정확한 비용 측정 가능성 미검증 |

원문 작성 당시에는 기획 문서만 작성했고 코드·환경·조직·세션은 변경하지 않았다. 당시 문서 검사(UTF-8, 일본어 본문, 범주, 제목, URL, 코드 펜스)는 구현 인수·실행 성능·실제 로그 호환성의 증거가 아니다.
