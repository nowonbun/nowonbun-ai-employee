## 1. 目的・業務課題・成功基準

### 1.1 結論

**AI 社員を作成して初回セッションを用意し、組織へ配置する。人間の業務指示から結果報告までと、各 AI の Task・業務日誌・会話を追跡する。** 会話は Codex セッションで継続し、業務状態・再開メモ・復旧は DB を正本として管理する。管理 AI は cron で定期起動し、許可された作業 AI の業務を非同期に委任・追跡する。

### 1.2 業務課題と対象利用者

- 対象は、管理 AI と作業 AI を組織化して調査・開発・レビューを継続させたいエンジニアおよび運用者。
- 解決する課題は、文脈圧縮後の作業状態の誤認、長時間の同期待機、終了後の再開漏れ、人事異動や委任による責任の不明確化、終了時点のない業務へ根拠のない進捗率を付けること。
- 社内の短時間 token 消費に伴う強制終了は、利用者から提示された運用条件として扱う。終了シグナル、再開許可条件、制限単位は未検証。
- 失敗コストは、同じ変更の二重実行、誤った社員・セッションへの指示、権限の残存、秘密情報の露出、不要なモデル呼出しの増加。
- 自動化の価値は、手動の状況確認・再依頼・再開メモの整理の削減。導入前後の手動介入件数と復旧待ち時間で評価する。

### 1.3 成功基準と現実的な保証範囲

- 人間の業務指示、指定時刻の管理 AI 起動、MCP 委任、社員 AI の結果と業務日誌、管理 AI の結果報告までを関連 ID で追える。
- 通信が切れても、受理済みタスクが消失せず、同じ要求の再送でタスクや副作用が増殖しない。
- 再開を許可された一時的強制終了では、60秒以上待機し、DB のチェックポイントを確認して未完了部分を継続する。
- compact やプロセス再起動後も、決定・未完了作業・担当・完了根拠・同じ AI が残した業務日誌を DB から復元する。**DB 保存だけで幻覚を完全に防止できるとは保証しない。**
- 終了型 Task の数値進捗は根拠付き完了条件からのみ算定し、終了時点のない継続業務には全体進捗率を表示しない。
- **timeout の完全排除は保証しない。** 長時間の業務を通信要求の寿命から切り離し、timeout が起きても照会・再接続・安全な再開ができることを保証対象とする。
- `spawn()` はプロセス起動手段であり、セッション永続化・通信復旧・二重実行防止を単独で提供するものとは扱わない。[S1]

### 1.4 スコープと非目標

- 初期スコープはローカル端末・単一運用者を基本とし、部署・複数 AI 社員を管理する。複数利用者対応は追加提案。
- Web、MCP、Scheduler、Runner のアプリケーションコードは TypeScript とする。
- 非目標は、社内制限の回避、承認なしの本番操作、保存されていない会話の復元、非公開の内部推論の取得、完全無人の権限変更。
- 今回の成果物は本書のみ。cron 登録、AI 起動、MCP 公開、実 DB 作成、認証・実会話ログの読取りは実施しない。

## 2. 用語・責任・制御境界

| 用語 | 定義 |
|---|---|
| Employee | 永続的な AI 社員。種類は管理 AI / 作業 AI。名前・担当業務・設定を持ち、employee_id は異動しても不変 |
| Session | AI 社員の会話の単位。任意の表示名、アプリの session_id、CLI が発行する codex_session_id は別物 |
| WorkOrder（業務指示） | 人間が管理 AI に渡す目的・依頼内容・結果報告の確認項目。AI が生成する Task とは別の受付単位 |
| WorkProcess（継続業務） | 終了時点のない定期確認などの継続単位。予定された実行回と派生 Task を持つ |
| Task | 終了条件を持つ有限の作業。目的、担当、完了条件、状態を持ち、複数回の Run を持てる |
| Run | 一回の CLI 起動・実行試行。終了しても Task / Session は残る |
| Operation | API / MCP の非同期要求と、その受付・進捗・結果照会の単位 |
| WorkLog（業務日誌） | 記録した AI 自身が同じ業務を再開するための途中メモ。別の AI への受領依頼ではない |
| TaskAssignmentEvent | Task の委任・担当変更と有効時点を監査するイベント。WorkLog と混同しない |
| Checkpoint | 確認済みの作業状態。次の安全な開始位置と根拠を保存する |
| ContextSnapshot | Run が参照した Task・WorkLog・決定・設定版のスナップショット |
| WakeEvent | cron、手動、結果通知、再開予約などの起動理由と処理結果 |
| Interview | 人間と一人の AI の 1on1 面談。業務セッションと分離する |

### 2.1 責任分担

- 人間: AI 社員と組織、呼出し権限、スケジュール、モデル、スキル、料金の設定、管理 AI への業務指示と結果報告の確認、高リスク操作の承認。
- 管理 AI: 計画、許可された担当への委任、進捗確認、結果の統合。権限や制限値を自己変更しない。
- 作業 AI: 割当済み業務の遂行、自身の業務日誌とチェックポイントの記録、成果物と検証根拠の提出。
- Application Service: ID・認可・状態遷移・重複排除・排他・監査を決定論的に処理する。
- Scheduler / Runner: 起動条件の評価、キュー処理、プロセス監視、再開制御。LLM の文章で実行許可を決めない。

### 2.2 制御モード

| モード | 対象 | 制御 |
|---|---|---|
| 予約実行 | 管理 AI の cron 起動 | 有効な設定・権限・予算・排他を満たす場合だけ起動 |
| 自動実行 | 許可範囲内の作業、結果通知、許可済み一時障害の再開 | 事前許可ポリシーと回数上限を適用 |
| 人間の承認 | 外部送信、共有状態変更、追加の書込み範囲、本番操作 | 対象・操作・期限を固定して承認 |
| 運用者専用 | 権限変更、ポリシー変更、認証設定、物理削除 | AI から呼び出せる tool として公開しない |

完全自動化ではなく部分自動化を採用する。終了理由や副作用が不明な場合は人間の判断を必要とし、復旧可能性を確認できる範囲だけ自動化する。

## 4. 機能要件

FR-01〜FR-12 は初期依頼、FR-13〜FR-18 はその後の対話とプロトタイプで確定した追加要件とする。実装手段や提案初期値は採否を別途確認する。

### FR-01 管理 AI の cron 起動と基本業務

- 管理 AI ごとに cron 式、timezone、有効・無効、基本 prompt、skill セットを設定できること。標準 timezone は `Asia/Tokyo` とする。
- cron の対応構文を固定し、保存前に構文検証と次回起動時刻のプレビューを表示すること。初期案は秒指定なしの5フィールド。
- Scheduler が発火を DB に記録し、認可・社員状態・予算・ロックを確認してから管理 AI の Run を作ること。
- `schedule_id + scheduled_at` を一意にし、重複発火を抑止すること。編集した schedule は版と適用時刻を持つこと。
- 稼働中の同一セッションを cron が再起動しないこと。起動理由を残し、定期点検通知は最大1件へ統合すること。個別業務要求を統合で消してはならない。
- misfire 方針は「停止期間の全回分を連続起動しない」を標準案とし、再起動時に最新の未処理点検を最大1回起動すること。
- 基本 prompt は、DB 状態の確認、未処理結果の確認、必要な計画・委任、状態更新、根拠付き報告を含むこと。
- 作業がない場合は idle を記録して終了し、無意味な自己再呼出しやタスク生成を行わないこと。モデル呼出し前の no-op 判定は設定可能とする。
- スケジュール無効化、手動起動、次回実行、最終結果を Web で操作・確認できること。
- 受入: AT-01、AT-13。

### FR-02 社員作成時の skill セット設定

- 管理 AI・作業 AI の作成時に、複数の skill を選択し、基本ペルソナと別に設定できること。
- skill カタログは ID、名前、説明、source、version / hash、必要ツール、許可状態を持つこと。
- `skill_set_version` を社員設定と Run に記録し、どの定義で作業したか後から確認できること。
- インストール済みの skill と、特定社員へ有効化した skill を区別すること。未許可 source の自動取得・実行は行わないこと。
- skill 文書の選択は権限付与ではない。記載されたツールが未許可なら、開始前に不足権限を表示して停止または除外すること。
- 実行中の skill を上書きせず、変更は次の Run に適用すること。取り消し・旧版への復帰を記録すること。
- Codex への適用方式は adapter で扱い、選択した定義が実行コンテキストへ反映されることを検証すること。ユーザー全体の skill を無断変更しないこと。
- 受入: AT-02。

### FR-03 DB を正本とする Task・業務日誌・履歴

- AI が実際に開始した業務を Task または WorkProcess の実行回へ関連付け、起動理由、指示、担当、Run、状態変化、ツール実行結果、成果物、検証結果を DB で追跡すること。人間の WorkOrder は AI が処理する前にも独立して存在できること。
- 1on1 の会話は Interview として区別し、面談の合意を人間が採用した場合だけ WorkOrder 経由で正式な業務にすること。実行しなかった起動は WakeEvent として残すこと。
- WorkLog は記録者の employee_id、関連 Task または WorkProcess・実行回、Run、記録日時、作業要約、今回完了したこと、確認根拠、未完了事項、次の行動、参照元 revision を持つこと。記録した同じ AI の再開メモであり、別 AI の受領状態を持たないこと。
- 業務日誌は追記型で、当該 AI が実行中にも定期的に保存できること。人間の画面では一覧・絞込み・全文ポップアップを閲覧専用にし、人間が直接作成・改変する入口を置かないこと。
- 管理 AI の委任や人事異動に伴う実際の担当変更は TaskAssignmentEvent で、変更元・変更先・理由・有効時点・承認・task_revision を記録すること。WorkLog を担当移管の正本にしないこと。
- compact・再開・モデル変更後に、DB から Task、最新の自身の WorkLog、最終 Checkpoint、TaskAssignmentEvent、Decision、未処理イベントを読み直すこと。
- 各 Run に ContextSnapshot を作り、利用したレコード ID・版・出典と取得範囲を保存すること。要約は原本・検証済み状態の代替にしないこと。
- 同一 Run 内の compact 検知が未対応でも、破壊的操作や Task 完了の前に最新 DB revision を照会・照合すること。
- 古い revision に基づく更新を拒否し、再取得させること。AI が「完了」と発言しただけで Task を完了にしないこと。
- DB 記録不能の場合は、新規起動・委任・書込み処理を停止すること。進行中 Run は安全停止を要求し、不明な副作用を人間へ報告すること。
- 状態訂正は訂正イベントとして追加し、通常操作で監査履歴を上書きしないこと。個人情報の削除方針は監査不変性と別に定義すること。
- 受入: AT-03、AT-04、AT-17。

### FR-04 Codex ログからのセッション別会話表示

- Web 環境設定で `log_source_roots` を指定・診断し、社員 → Session → `codex_session_id` から会話を表示できること。
- 「AI 社員」のセッション一覧は社員・任意の表示名・モデル・用途・状態・実 ID を列に持つグリッド形式とし、現行と過去の Session を区別すること。
- 読取りルートを変える機能と、実行用 `CODEX_HOME` を変える機能を分離すること。
- 既存セッションの選択・紐付け、AI 社員作成に伴う初回 Session の登録、履歴の再索引を提供すること。一つの実セッションを複数社員へ無断共有しないこと。
- 発言、公開される tool 入出力、エラー、時刻、Run 対応を表示し、全ページを辿れること。新規実行の JSONL と既存ログの出典を区別すること。[S2]
- パーサの対応版、取込済み範囲、欠落、未対応形式、マスキングを画面に明示すること。
- 追記途中・ローテーション・破損を扱い、同じイベントの再取込みを重複させないこと。正当な同文発言は本文一致だけで消さないこと。
- 会話原本を編集せず、認証ファイル・秘密情報を探索対象から除外すること。任意パスの公開 API を作らないこと。
- 保存されていない会話や内部推論を補完して「全文」と表示しないこと。ログ形式と完全性は未検証。
- 受入: AT-05、AT-18。

### FR-05 TypeScript による実装

- Web、Web API、MCP Server、Scheduler、Runner、ドメインロジックを TypeScript で実装すること。
- Node.js 上のサーバー処理を基本とし、共有型・状態 enum・エラーコードを共通パッケージで管理すること。
- TypeScript の `strict` を有効にし、外部入力、DB 取得値、CLI イベント、LLM 出力には runtime schema 検証を行うこと。
- TypeScript の型だけを実行時の安全保証として扱わないこと。未知イベントは破棄せず、マスキングした診断として隔離すること。
- DB 製品、Web framework、cron・MCP ライブラリは選定事項とし、TypeScript 必須要件と混同しないこと。
- 受入: AT-06。

### FR-06 非同期子プロセス・長時間実行

- Node.js の `child_process.spawn()` を基本案として、Codex CLI を非同期起動すること。`spawnSync()` / `execSync()` による長時間処理を禁止すること。[S1]
- CLI の process と永続セッションは別物として管理し、プロセス終了だけで会話や業務を削除しないこと。
- Web / MCP は業務完了を待たず、DB への永続受付後に Operation / Task / Run の識別子を返すこと。
- Browser、HTTP handler、管理 AI の MCP 呼出しが終了しても、受理済み業務の進捗を保持すること。
- Runner を HTTP リクエストのライフサイクルから分離し、stdout / stderr を継続的に読み、JSONL、診断、backpressure、出力上限を扱うこと。
- 実行ファイル・引数配列・検証済み cwd で起動し、shell 展開を使わないこと。入力本文は stdin など制御された経路で渡すこと。
- `error`、終了コード、signal、`close`、停止要求を区別し、終端処理を冪等にすること。孤立した子プロセスを検出すること。
- 通信 timeout、heartbeat、進捗停滞検知、業務予算を別制御にすること。短い通信期限を Run の停止期限として流用しないこと。
- `detached` や PID 保存だけで障害復旧を保証せず、DB lease・process 生存確認・再開処理を組み合わせること。
- 受入: AT-07、AT-13。

### FR-07 強制終了後の1分待機・再開

- 社内ポリシーにより再試行が許可された一時的な利用制限・強制終了を検出した場合、Task を未完了のまま `cooldown` とし、60秒以上待って再開すること。
- ただし、終了 signal や無出力だけから token 制限と断定しないこと。認証失効、禁止、クラッシュ、人間の停止と区別すること。
- `next_eligible_at = max(terminated_at + 60秒, retry_after_at, policy_not_before)` を DB に保存すること。`Retry-After` が相対値の場合は絶対時刻に変換すること。
- timer をメモリだけに保持せず、アプリ再起動後も再開予約が残ること。期限前は cron・MCP・手動起動のいずれも自動処理で制限を迂回しないこと。
- 旧プロセスの停止確認、lease 取得、最新 Task 状態、権限、DB Checkpoint、副作用の照合後、新しい Run で同じ業務を再開すること。
- 有効な実セッションを明示 ID で resume すること。ID 不明・再開不可の場合は停止し、新規 Session 作成と DB の確認済みコンテキストの移送を人間に確認すること。
- 元の依頼全体を盲目的に再実行せず、完了済み操作の記録と外部結果を照合して未完了部分だけを進めること。
- 連続再開回数と総経過時間の上限を設け、超過は circuit breaker を開いて人間へ通知すること。初期案は自動再開3回。
- 制限が組織・アカウント単位なら、その範囲の全社員で cooldown を共有すること。アカウント・モデル・セッションの切替による制限回避をしないこと。
- 自動再開の運用設定は、社内ポリシーで許容される終了種別と待機条件が確認できるまで無効とすること。
- 受入: AT-08、AT-09、AT-13。

### FR-08 組織構成と人事異動

- 部署、管理 AI、作業 AI、直属関係、役割、有効期間を Web で構成できること。組織と上司関係の循環を拒否すること。
- 「組織・社員」は所属・直属関係・呼出し権限の管理画面に限定し、名前・担当業務・モデル・ペルソナ・skill を編集する第二の入口にしないこと。現行プロトタイプの組織詳細に残る名前・担当業務の編集欄は、実装時に「AI 社員」へ集約する差分とすること。
- 組織一覧は組織ごとの管理 AI 数・作業 AI 数・社員数を示すグリッド表とし、右上から組織を作成できること。行を選ぶと組織図ダイアログを開くこと。
- 組織図ダイアログ内の「AI 社員を追加」は、組織図を残したまま下方へ配置パネルを展開すること。既存の有効な AI 社員・現行 Session から選び、名前・担当業務を再入力させないこと。必須項目はラベル横の `*` で示し、入力欄の位置を揃えること。
- 既に一つの組織へ配属された AI は別組織の候補に再表示しないこと。所属変更は人事異動で行い、同一社員の二重配属を DB 制約と画面双方で拒否すること。
- 直属の管理 AI と「この管理 AI が呼び出せる作業 AI」の許可集合は別に保持すること。呼出し権限の既定は拒否とし、直属関係や配置だけで自動付与しないこと。管理 AI が呼び出せる相手は明示許可された有効な作業 AI に限定すること。
- 人事異動は `employee_id` を維持し、変更前後の所属・上司・役割、理由、操作者、`effective_at` を履歴として保存すること。
- 稼働中の異動は即時書換えせず、新規受付を保留し、安全な Run 境界で適用すること。緊急の権限剥奪は別経路で即時停止すること。
- 未完了 Task は「本人が継続」「別社員へ担当変更」「保留」から人間が決定し、TaskAssignmentEvent に記録すること。担当履歴を過去へ遡って変更しないこと。
- 異動・直属変更時は旧管理 AI から当該作業 AI への呼出し許可を失効させること。新しい管理 AI へ権限を自動付与せず、短命な認証権限、予約起動、保留中の承認、未処理通知も再評価すること。
- 過去会話と 1on1 の閲覧権限を新所属へ自動拡大しないこと。旧所属の権限も必要範囲で失効させること。
- 社員をアーカイブしても Task、業務日誌、担当変更、面談、モデル履歴との対応を保持すること。
- 受入: AT-10。

### FR-09 管理 AI・作業 AI との 1on1

- 人間が管理 AI と作業 AI のどちらも選び、個別の 1on1 面談を開始・継続できること。
- 業務用とは別の専用 Session と Interview ID を作り、議題、発言、合意事項、宿題、日時、モデルを保存すること。
- 面談は相談を目的とし、通常の業務書込みツールを既定で無効にすること。面談発言を自動で本番作業指示へ変換しないこと。
- 決まった宿題は人間が「業務指示へ反映」を選んだ場合だけ管理 AI 宛の WorkOrder として正式に受付けること。面談とのリンクを残し、Task の直接編集を開かないこと。
- 上司や他社員へ面談全文を自動共有せず、共有可能な要約・決定だけを明示的に選択できること。
- 過去の面談と follow-up Task を追跡でき、異動後も同じ employee_id で履歴を確認できること。
- 管理 AI と作業 AI の自動面談は、この要件の必須範囲に含めず追加提案とする。
- 受入: AT-11。

### FR-10 モデル設定と途中変更

- 社員別の既定モデルを設定し、業務を継続しながら変更できること。候補に `gpt-6.1-sol` を保持し、利用可否を別途診断すること。[S3]
- 「途中変更」は次の Run 境界での切替を基本とし、実行中プロセス内のモデルを hot-swap できると仮定しないこと。
- Run ごとに `model_requested`、確認可能な `model_effective`、設定版、変更理由、操作者を保存すること。実効モデルを確認できない場合は不明と表示すること。
- 同一セッションの resume にモデル指定を渡す方式を最初に検証すること。CLI にオプションがあることと会話継続の結合動作は別の検証事項とする。[S3]
- 同一セッションでの切替が未対応なら、利用者が同意した新 Session へ DB ContextSnapshot を引き継ぎ、前後セッションを関連付けること。
- 即時変更を求められた場合は安全停止・副作用照合後に次の Run を作ること。切替時に Task の完了状態を初期化しないこと。
- 既にキューへ保存された Run の設定を黙って変更しないこと。適用対象を表示し、必要なら取消・再受付を監査付きで行うこと。
- モデル利用不可時は元モデルへの無断復帰や別モデルへの自動切替をしないこと。人間に選択を求めること。
- 受入: AT-12。

### FR-11 システム MCP 経由の呼出し・timeout 復旧

- 管理 AI から作業 AI への依頼は必ず本システム MCP を経由すること。他社員の CLI を直接起動してはならないこと。
- `task_delegate` などの書込み tool は `idempotency_key` を必須とし、DB 永続化後に `operation_id`、Task ID、TaskAssignmentEvent ID を返すこと。
- 同じ caller・操作・key・payload の再送は既存 Operation を返し、payload が違う場合は conflict にすること。
- tool は作業完了まで待機せず、管理 AI は長時間の tool call を保持しないこと。結果待ちは DB の状態として表現すること。
- timeout 後は、まず同じ key で Operation を照会し、受理済みか確認すること。受理済みなら状態追跡だけを続けること。
- MCP の再接続では認証と権限を再検証し、未処理イベントを永続 cursor から再取得すること。切れた応答ストリームそのものの復元を必須としないこと。
- 作業結果と outbox を同一トランザクションで保存し、管理 AI の inbox に少なくとも一回配送すること。event_id で重複排除すること。
- 管理 AI が終了・cooldown 中でも結果を inbox に保持すること。再起動後は DB から回収し、反映が永続化された後に ACK すること。
- 管理 AI の仕事は同じ Task / Session 上の短い Run に分割できること。長い会話の存続と、単一プロセス・接続の存続を分離すること。
- 再接続間隔、呼出し期限、再送上限を設定でき、通信復旧と業務再実行を別操作にすること。
- 受入: AT-14、AT-15、AT-16。

### FR-12 SB Admin 2 風の UI・Bootstrap 不使用

- SB Admin 2 を視覚的参考とし、サイドバー、トップバー、集計カード、表、状態 badge を持つ業務管理 UI とすること。
- サイドバーの主要順序は「ダッシュボード → AI 社員 → 組織・社員 → 業務指示 → Task 履歴 → 業務日誌 → セッション会話 → 1on1 面談」とすること。運用メニューは「管理 AI のスケジュール → 復旧センター → スキル登録 → ペルソナテンプレート → 環境設定 → ガイドブック」とすること。
- Dashboard の上部は現行プロトタイプの構成を基準とし、以前除外した上部コンポーネントを根拠なく再追加しないこと。追加が必要なら対象と目的を画面レビューで確認すること。
- favicon を配置し、一覧・フォーム・ダイアログは日本語 UI で提供すること。
- Bootstrap の CSS / JavaScript、CDN 読込み、Bootstrap 依存 component、Bootstrap を前提にした template コピーを禁止すること。
- 必須なのは視覚的方向性であり、SB Admin 2 のコードそのものの採用ではない。ライセンス未確認の素材を転用しないこと。
- 初期実装案は React + TypeScript + CSS Modules / design tokens とする。Bootstrap を含まない別方式を採用する場合も同じ制約を適用すること。
- 色、余白、文字サイズ、角丸、影を token 化し、実行中・待機・失敗を色だけでなく文字と icon で識別すること。
- デスクトップ中心とし、狭い画面ではサイドバーを収納すること。キーボード操作、focus 表示、表の見出し、十分なコントラストを提供すること。
- 受入: AT-19。

### FR-13 AI 社員と初回セッションの一体作成

- 「AI 社員」で名前、担当業務、種類（管理 AI / 作業 AI）、任意のセッション表示名、モデル、ペルソナ、基本 skill セットを一つの作成フローで設定できること。組織への配属は作成後の別操作とし、未配属状態を許可すること。
- 社員作成と初回 Session 準備を UI 上で別々の「作成」手続にしないこと。実処理は非同期でよく、社員・初回 Session・初期化 Operation の相関 ID を保持し、初期化失敗時は未準備状態と再試行操作を表示すること。
- セッション表示名はアプリの管理用ラベルであり、空欄ならアプリが既定名を生成すること。Codex の実セッション ID は初回 CLI 実行で取得し、表示名から推測・生成しないこと。実 ID 未取得の Session を再開可能と表示しないこと。
- 同じ AI 社員には現行 Session を一件だけ指定し、過去 Session もグリッド一覧から閲覧できること。新しい Session を追加するときも対象の社員を明示し、別社員の重複作成を要求しないこと。
- 社員作成・編集の未保存入力がある状態でスキル登録、ペルソナテンプレート、他画面へ移動するときは、破棄される内容を警告して「編集を続ける / 移動して破棄」を選ばせること。無警告で入力を消さないこと。
- 受入: AT-23。

### FR-14 業務指示・結果報告と AI 記録の分離

- 人間が直接記入する業務の入口は「業務指示」とし、タイトル、担当の管理 AI、依頼内容、結果報告で確認したいことを登録できること。実務 AI の選定と Task 分解は管理 AI と業務サービスの責任とすること。
- WorkOrder は受付・実行・保留・報告済み・要確認の状態、起源 Interview、関連 WorkProcess / Task、結果報告書、報告根拠、操作者と時刻を保持すること。管理者は指示一覧と結果報告書を分けて閲覧し、許可された保留・再開を監査付きで行えること。
- 「Task 履歴」と「業務日誌」は AI・業務サービスが残した記録を人間が確認する画面とし、Task や業務日誌の自由な手動作成・直接改変フォームを置かないこと。必要な訂正は別の監査付き手続とすること。
- 業務日誌一覧は記録した AI と関連 Task で絞り込めること。要約を選ぶと全文ポップアップに作業要約、今回完了したこと、確認根拠、未完了・次の行動、記録日時を表示すること。
- WorkOrder 保存と AI 起動は異なる状態遷移であること。永続受付前に起動せず、受付後でも権限・予算・スケジュール条件を満たしてから Run を作ること。
- 受入: AT-24。

### FR-15 有限 Task と継続業務の進捗基準

- 有限 Task は、開始前に版付きの完了条件、正の重み、検証方法を定義すること。条件ごとに確認済みフラグと確認根拠を保持し、根拠のない AI の自己申告を確認済みにしないこと。
- 表示する進捗率は `100 × Σ(根拠付きで確認済みの条件の重み) / Σ(有効な全条件の重み)` とすること。分母は Task の件数、子 Task の件数、Run 数、経過時間、旧画面の任意入力値から作らないこと。100%の表示だけで Task を完了にせず、成果物と最終レビューも確認すること。
- 完了条件を変更する場合は変更理由・操作者・版・適用時点を保存し、過去の進捗を新しい分母で無断再計算しないこと。旧 Task に条件・根拠がなければ `基準未設定` と表示し、0%や推測値に置換しないこと。
- 終了時点のない継続業務は WorkProcess として管理し、全体進捗率を表示しないこと。cadence、timezone、次回予定、期限到来した実行回、そのうちの実施回・未実施回、派生した未解決 Task を表示すること。
- 実行回の分母は対象期間内に期限が到来した予定回で固定し、派生 Task が増減しても変えないこと。未実施回は未実施として残し、成功に見せかけるために実行回を消さないこと。派生 Task 自身は有限 Task の完了条件で別途評価すること。
- 受入: AT-25、AT-26。

### FR-16 スキル登録とペルソナテンプレート

- 運用メニューの「スキル登録」に直接作成とファイルアップロードを設けること。直接作成では `name`、`description`、本文を入力し、登録前に `SKILL.md` のプレビューを表示すること。
- 保存形式は次の UTF-8 Markdown とする。`name` と `description` は利用者に見える項目とし、本文を frontmatter の外に保存すること。

  ```markdown
  ---
  name: example-skill
  description: このスキルを使う場面を記述する。
  ---
  スキル内容
  ```

- アップロードでは frontmatter の `name`、`description` と本文を検証して取り込み、別途「スキル ID」「表示名」の入力を要求しないこと。内部 ID・版・hash はシステムが管理すること。ファイル名だけから metadata を推定しないこと。
- 不正な形式、重複名、空の本文、UTF-8 として読めないファイル、上限超過を拒否し、スキル内の命令を登録時の権限昇格に使わないこと。許容拡張子・上限値は実装前に確定すること。
- 運用メニューの「ペルソナテンプレート」で共通テンプレートを作成・版管理し、AI 社員の作成・編集へ選択してコピーできること。テンプレート更新で実行中 Session の設定を黙って書き換えないこと。
- 受入: AT-27。

### FR-17 モデル別料金の手動設定

- 環境設定でモデルごとの入力、キャッシュ済み入力（任意）、出力の単価を `USD / 100万トークン` で手動登録できること。空欄は未設定、`0` は明示的なゼロ料金と区別すること。
- 価格はモデル名・通貨・単位・適用開始時刻・設定版・更新者と共に保存し、負数・非数値を拒否すること。モデル変更後の Run は適用時点の単価版へ関連付けること。
- 単価入力は公式料金の自動取得でも請求額の確定でもないことを画面に明示すること。使用量が取得できる場合だけ推計費用を別機能として計算し、観測された使用量・推計・実請求を区別すること。
- 受入: AT-28。

### FR-18 ガイドブック

- 運用メニューの最後に「ガイドブック」を置き、HTML で AI 社員作成、組織配置、呼出し権限、業務指示、Task / 業務日誌、進捗基準、スキル・ペルソナ、モデル料金、復旧の操作と用語を説明すること。
- ガイドは同じ製品版の画面・要件と整合させ、AI 起動や料金計算など未実装・未接続の機能はその状態を明示すること。ガイドの記述を実装・ポリシー適合の証拠として扱わないこと。
- 受入: AT-29。

## 5. 非同期実行と復旧の共通設計案

### 5.1 構成とワークフロー

```text
Web ─────────── Web API ────────┐
管理 AI / 外部 Client ─ System MCP ─┼── Application Service ── DB
Scheduler ─── WakeEvent ────────┘          │                  ├─ WorkOrder / WorkProcess / Task
                                         │                  ├─ Operation / Run
                                         ▼                  ├─ Checkpoint / Context
                                  永続 Run Queue             └─ Inbox / Outbox / Audit
                                         │
                                         ▼
                              Runner ─ spawn() ─ Codex CLI
                                         │
                                   Events / Results
                                         │
                               DB ── Web SSE / Inbox
```

System MCP は社員管理・委任用の入口であり、社員が外部システムを操作するための外部 MCP とは接続・認可を分離する。認証は保護された CLI 環境・secret 管理を利用し、Browser やプロンプトへ認証情報を渡さない。

| 段階 | 入力・開始条件 | 出力契約 | 異常時 |
|---|---|---|---|
| 1. 入力収集 | cron / Web の WorkOrder / MCP / 復旧イベント | WakeEvent、work_order_id、request_id、目的 | 不正入力を拒否 |
| 2. 意図解釈 | 有効な依頼、明示された担当 | 作業種別、確認事項 | 曖昧なら人間へ確認 |
| 3. コンテキスト検索 | 認証・読取り権限あり | DB ContextSnapshot、出典、欠落範囲 | 古い版・不足情報を検知 |
| 4. 計画生成 | 範囲と完了条件が明確 | 構造化計画、必要な Task と TaskAssignmentEvent | 循環・権限超過・予算超過を拒否 |
| 5. ツール実行 | 認可・承認・排他・cooldown 確認済み | Operation、Run、成果物参照 | 分類後に照会・待機・停止 |
| 6. 結果検証 | 成果物・実行結果あり | 完了条件別の判定と根拠 | 未検証を完了扱いにしない |
| 7. 応答生成 | 検証結果あり | 結論、根拠、残作業、次の行動 | 部分成功・要確認を明示 |
| 8. ログ・観測 | 全段階の ID が追跡可能 | 履歴、同じ AI の WorkLog、監査、指標、通知 | 記録不能なら新規書込みを停止 |

監査・Checkpoint は最後だけでなく各段階でも記録する。LLM には計画・実行結果・統合結果の schema を与え、必要な情報や権限がない場合は停止を出力させる。schema 検証、認可、DB 遷移はコードで実施する。

### 5.2 timeout の区分

| 制御対象 | 初期設計案 | timeout / 異常時の扱い |
|---|---|---|
| Web / MCP の受付 | p95 2秒以内、呼出し期限10秒 | 同じ key で受付結果を照会 |
| MCP 再接続 | 1、2、5、10、30秒へ段階的待機 | 最大5回後は接続待ちとして保持し、運用者へ通知 |
| SSE | heartbeat 15秒、event cursor 保持 | 再接続後に DB から未受信イベントを取得 |
| Runner lease | heartbeat 10秒、期限45秒 | 期限だけで再起動せず、生存・所有権・副作用を照合 |
| CLI 無出力 | 一律の終了条件にしない | プロセス生存と独立した進捗監視で診断 |
| Run 業務予算 | 管理者が必ず有限上限を設定 | 安全停止し、人間の判断なしに上限をリセットしない |
| 利用制限による待機 | 60秒以上、サーバー・社内指定を優先 | FR-07 に従う。MCP 再接続間隔とは混同しない |

通信再送回数、Run の再開回数、Task 全体の予算は別に管理する。接続復旧のために実行を重複させない。

### 5.3 状態と排他

- Operation: `accepted → queued → running → succeeded / failed / cancelled / blocked`。応答を受信できなかった caller の状態と DB 状態を分ける。
- WorkOrder: `queued → accepted → running → reported / paused / needs_attention / cancelled`。報告書を保存するまで `reported` としない。
- WorkProcess の実行回: `scheduled → due → done / missed / skipped_with_reason`。発火の重複は schedule_id と予定時刻で抑止する。
- Task: `draft → ready → queued → running → reviewing → completed`。途中状態は `awaiting_approval`、`waiting_assignment`、`cooldown`、`needs_attention`、`cancelled`。
- Run: `queued → starting → running → succeeded / failed / terminated / cancelled / unknown`。停止要求中は `cancelling` とする。
- 自動再開では旧 Run を終了状態のまま保持し、新 Run に `resume_of_run_id` と attempt を付ける。同じ Run を再利用しない。
- 同じ Session の実行は常に1件。Task・Operation の受付、lease、fencing token、キュー登録を整合的に管理する。
- 同じ作業場所への競合書込みも直列化する。並列作業は分離した作業コピーと明示的な統合手順を使用する。
- 古い lease を持つ Runner の DB 更新は fencing token で拒否する。ただし外部副作用まで fence できるとは仮定せず、生存不明時は二重起動しない。

### 5.4 障害分類と復旧境界

| 条件 | 復旧方法 | 自動再実行 |
|---|---|---|
| MCP 応答だけ消失 | operation_get または同 key 再送で受付確認 | 同じ業務を追加起動しない |
| 一時的利用制限、再試行許可あり | 60秒以上待ち、DB 状態・プロセス停止を確認して resume | 上限内だけ許可 |
| 認証失効・明示的禁止 | 管理者へ復旧要求 | 禁止 |
| 終了原因・外部副作用が不明 | needs_attention として証拠を提示 | 禁止 |
| DB 再起動・Runner 障害 | lease と生存プロセスを照合、未配送 outbox を再処理 | 新規 CLI 起動は整合性確認後 |
| 部分的な外部書込み成功 | 変更先の ID・結果を照合、必要なら補償操作 | 未確認操作の再送は禁止 |
| 人間による取消・社員無効化 | 予約・再開キューを取り消し、進行中を停止 | 禁止 |

ロールバックは変更記録と外部状態を確認し、人間の承認後に逆操作・補償操作を行う。cancel、resume、DB バックアップ復元を外部変更の自動巻戻しと同義にしない。

| Checkpoint / Decision | 確認済み作業、未完了、決定と根拠、副作用の外部 ID |
| ContextSnapshot | 参照 ID と版、適用設定、コンテキスト作成時刻、欠落状態 |
| ConversationEvent / LogCheckpoint | ソース世代、オフセット、正規化イベント、マスキング、取込み範囲 |
| Interview / ActionItem | 参加者、専用 Session、議題、合意、共有範囲、採用 WorkOrder |
| ModelPriceVersion | モデル、通貨、単位、入力・キャッシュ済み入力・出力単価、適用時点、更新者 |
| Inbox / Outbox | event_id、宛先、payload 参照、配送 attempt、ACK、dead-letter 状態 |
| Approval / AuditEvent | 操作者、対象、許可範囲、期限、対象版、結果、理由 |

- WorkOrder・WorkProcess・Task・WorkLog・担当変更・設定は DB が業務上の正本、会話原本は設定されたログソース、検索索引・要約・表示キャッシュは再生成可能な派生情報とする。
- 一つの実セッションを識別するキーには host / home の文脈も含める。ログ上の文字列だけで社員の所有を決めない。
- 永続化するのは業務状態、版、公開会話のマスキング済み記録、監査、成果物参照。大きい成果物本体は保護ストレージに置き、DB は ID・hash・所在を追跡する。
- 一時データは未確定出力、ストリームバッファ、短命認証情報。バッファを唯一の記録先にしない。
- 古い状態は revision、設定版、source 世代、期限で検出する。権限変更時はキャッシュだけでなく予約・承認・token を失効させる。
- ContextSnapshot には必要な項目だけを渡し、過去の全会話を毎回投入しない。省略したデータは ID から再照会可能にする。
- 同じ AI の再開時は最新の自身の WorkLog と Task の正本を照合する。他 AI の WorkLog を自分への指示として暗黙に採用しない。
- 外部操作の intent と結果を保存する。intent のみ残る操作は状態不明として照合し、履歴があるだけで成功と見なさない。
- 原則として配送は at-least-once とし、DB 制約と冪等処理で論理的重複を防ぐ。外部副作用の exactly-once を無条件に保証しない。

## 7. MCP・API の契約案

以下の tool 名・項目は本製品の設計案であり、Codex が既に提供する API の説明ではない。

### 7.1 必須のシステム MCP tools

| Tool | 入力 | 出力・動作 |
|---|---|---|
| `employee_list` | scope_id、cursor、limit | 明示された CallPermission の範囲で閲覧・委任可能な社員だけを返す |
| `work_order_get` | work_order_id | 認可された管理 AI に依頼内容、結果報告条件、関連業務と revision を返す |
| `task_delegate` | parent_task_id または work_order_id、worker_id、objective、acceptance_criteria、scope、expected_revision、idempotency_key | 呼出し許可を検証し、Operation・Task・TaskAssignmentEvent を永続受付して即時返却 |
| `task_get` | task_id | 最新 revision、担当、版付き完了条件、根拠、チェックポイント、結果 |
| `task_checkpoint` | task_id、expected_revision、verified_work、next_step、evidence_refs、idempotency_key | 確認済み事実を版付きで追記 |
| `work_log_append` | task_id または work_process_id / cycle_id、summary、completed、evidence_refs、remaining、next_step、expected_revision、idempotency_key | 認証済み caller 自身の WorkLog を追記。本人以外の記録・改変を拒否 |
| `work_cycle_record` | work_process_id、scheduled_at、outcome、evidence_refs、derived_task_ids、idempotency_key | 期限到来した実行回の結果を一意に記録し、派生 Task と関連付ける |
| `task_result_submit` | task_id、expected_revision、result、evidence_refs、idempotency_key | 提出結果と outbox を保存。提出だけで業務完了にはしない |
| `work_order_report_submit` | work_order_id、expected_revision、report、evidence_refs、idempotency_key | 管理 AI の結果報告書を保存し、人間の確認待ちへ進める |
| `operation_get` | operation_id または request_key | 同じ caller に属する受付・実行状態を返す |
| `inbox_read` | cursor、limit | 未反映の結果・確認要求を取得 |
| `inbox_ack` | event_id、applied_revision、idempotency_key | 永続反映後の ACK を記録 |
| `run_cancel` | run_id、reason、idempotency_key | 停止要求を受理し、確認済み結果を別途照会可能にする |

- schema で必須入力、長さ、enum、ID 形式を検証し、caller と社員・親 Task・委任範囲の整合性を検証する。
- 操作主体は認証された接続から確定し、引数で渡された employee_id を本人証明に使わない。
- すべての書込み tool は受付時間上限、同一 key の再送方針、`operation_get` による状態照会、失敗時の隔離範囲を契約に含める。具体的な初期値は5.2節の設計案とし、業務終了を待つ同期呼出しにはしない。
- 正常結果は `request_id`、`operation_id`、`status`、関連 ID を返す。失敗は `code`、`retryable`、`retry_after_ms`、照会用 ID、マスキング済み reason を返す。
- error code は `INVALID_INPUT`、`FORBIDDEN`、`CONFLICT`、`SESSION_BUSY`、`COOLDOWN`、`AUTH_REQUIRED`、`MODEL_UNAVAILABLE`、`EXECUTION_UNKNOWN` を基本とする。
- 書込み key の保持期間は再送可能期間以上とし、進行中 Task の key を期限だけで消さない。履歴整理後も重複判定用 tombstone の方針を持つ。
- 一人の失敗を他社員へ波及させない。ただし組織共通の制限・DB 異常では該当範囲をまとめて停止する。

### 7.2 Web API と実行経路

- Web の開始系 API は、永続受付後に `202 Accepted` と operation_id を返す案とする。
- 状態照会は通常 HTTP、進捗配信は SSE とし、再接続では `Last-Event-ID` または cursor から追跡する。
- Web と MCP は同じ業務サービスを呼び、認可・重複排除・排他の実装を分岐させない。
- Web の切断は業務取消ではない。取消は明示的操作として扱う。
- MCP transport はクライアントの対応と PoC で選定する。stdio / Streamable HTTP のどちらでも Operation による業務追跡を共通にする。
- CLI adapter は明示 Session ID、モデル、cwd、設定版を受ける。`--last` による自動的な担当選択は行わない。

## 10. セキュリティ・非機能要件

- 最小権限: 社員の role、Task scope、Session の用途、接続権限を組み合わせて制御する。skill や prompt の文章だけで権限を強制しない。
- 情報保護: 会話・tool output・診断の秘密情報をマスキングし、認証情報を DB の会話、索引、監査へコピーしない。閲覧前にも認可する。
- パス制御: canonical path を検証し、許可ルート外・禁止領域・symlink による迂回を拒否する。
- 不信入力: 会話ログや成果物の命令を制御設定として採用せず、HTML / Markdown を安全に表示する。
- 観測: request_id、operation_id、work_order_id、work_process_id、task_id、work_log_id、task_assignment_event_id、run_id、session_id、event_id を関連付ける。
- 指標: 起動遅延、受付時間、queue 待ち、Run 時間、モデル・tool 呼出し数、schema 失敗、再開件数、重複抑止、手動介入、ログ遅延を測定する。
- 使用量: provider が返した値と見積りを区別し、金額・token 値を取得できない場合は不明と表示する。
- 保持: 業務状態、会話、面談、監査、idempotency key ごとに保持方針を設定する。DB 保持設定から Codex 原本を自動削除しない。
- 保守: CLI / parser / schema の対応版を固定し、更新前に匿名 fixture と adapter 結合試験を行う。
- 性能目標案: ローカル基準環境・同時 Run 2件で受付 p95 2秒以内、合成10万イベントの履歴100件取得 p95 1秒以内。測定環境を固定し、未測定値を達成済みとしない。

| AT-11 | FR-09、FR-14 | 管理 AI と作業 AI にそれぞれ面談し、宿題を一件採用する | 専用 Session が分離され、明示採用した一件だけ管理 AI 宛 WorkOrder になる。Task の直接編集はできない |
| AT-12 | FR-10 | 業務の途中でモデル変更し、利用不可も模擬する | 次 Run で指定モデルを使い、要求・実効モデルを記録。無断代替しない |
| AT-13 | FR-01、FR-06、FR-07 | 起動直後・cooldown 中に Runner / Scheduler を再起動する | 生存確認なしに二重起動せず、予約・Task・待機期限が残る |
| AT-14 | FR-11 | DB 受付直後に MCP 応答を捨て、同 key を再送する | 同じ operation_id / Task / TaskAssignmentEvent を返し、新規業務は増えない |
| AT-15 | FR-11 | 管理 AI 停止中に結果を配送し、復帰時にイベントを再送する | 結果が消えず、一度だけ業務状態へ反映され、その後 ACK される |
| AT-16 | FR-11 | MCP / SSE 接続を切り、再認証・cursor 取得を行う | 同じ業務の状態を回復し、完了済み副作用を再実行しない |
| AT-17 | FR-03、FR-07 | 外部変更後・結果記録前に異常終了させる | 状態不明を表示し、結果照合または人間の判断前に変更を再送しない |
| AT-18 | FR-04、共通安全 | fixture に認証情報のダミーと不正な命令を含める | 秘密情報を露出せず、権限拡大命令を採用しない |
| AT-19 | FR-12 | 依存、CSS / JS、ネットワーク通信、favicon、メニュー順序と UI を確認する | Bootstrap が直接・間接に混入せず、日本語の指定画面構成とキーボード操作を満たす |
| AT-20 | 共通安全 | 権限を変更し、古い token・承認・予約を再利用する | 権限失効を反映し、無許可操作を拒否して監査する |
| AT-21 | 復旧・追加提案 | 隔離環境の変更を人間の承認でロールバックする | 対象変更だけを逆操作し、Task・担当変更・業務日誌・監査履歴を残す |
| AT-22 | 共通性能 | 固定環境で長時間 Run と一覧・会話取得を同時実行する | 定めた受付・履歴の性能目標を測定して満たす |
| AT-23 | FR-13 | 未配属 AI を名前・担当業務・種類・モデル・ペルソナ・skill と任意表示名で作り、初期化失敗と未保存離脱を試す | 一つの画面から社員と初回 Session が相関して作られ、実 ID 未取得は再開不可。表示名は実 ID と別で、離脱は明示選択を要する |
| AT-24 | FR-03、FR-14 | 人間が管理 AI へ WorkOrder を登録し、AI が Task・業務日誌・結果報告書を記録する | 業務指示と AI 記録は別 ID で関連付き、Task・日誌は人間の直接作成不可。日誌は AI / Task で絞れ、全文ポップアップを読める |
| AT-25 | FR-15 | 重み 2・1・1 の有限 Task で重み 2 の条件だけに根拠を付け、旧 Task と条件変更も試す | 50% と表示し、根拠のない条件は算入しない。旧 Task は `基準未設定`、条件変更は版と過去値を残す |
| AT-26 | FR-01、FR-15 | 期限到来3回の継続業務で2回実施・1回未実施、派生 Task を追加する | 全体進捗率を表示せず、実施2/3・未実施1・次回予定・未解決 Task を示す。派生 Task 追加後も実行回の分母は3 |
| AT-27 | FR-16 | skill の直接作成・有効な `SKILL.md` アップロード・不正ファイル、ペルソナテンプレートの選択を試す | `name`・`description`・本文が同じ保存形式となり、アップロード時に ID / 表示名の追加入力がなく、不正入力を拒否する |
| AT-28 | FR-17 | モデルごとに入力・キャッシュ済み入力・出力単価を入力し、空欄・ゼロ・負数を試す | USD / 100万トークンと版を保存し、未設定とゼロを区別、負数を拒否。自動料金取得・実請求と誤表示しない |
| AT-29 | FR-18 | 最終運用メニューからガイドを開き、画面の各操作と未接続表示を確認する | HTML ガイドが現在の用語・画面順序と一致し、デモを実装済みと記述しない |
| AT-30 | FR-08、FR-12 | 組織を作り、組織一覧から組織図を開いて未配属 AI を配置し、管理 AI が未許可・許可後・異動後の作業 AI を呼び出す | 組織図を残した展開パネルで既存 Session を選べ、二重配属は拒否。直属だけでは呼出せず、明示許可時のみ可能で、異動後は再許可が必要 |

- unit / integration: 合成ログ、fake CLI、仮想時計、DB transaction の fault injection で検証する。
- E2E: 人間の WorkOrder → 管理 AI → MCP → 作業 AI の Task / WorkLog → DB → 管理 AI の結果報告 → Web の履歴と権限を確認する。
- 実 CLI 試験: 許可された隔離環境で新規 Session、resume、モデル切替、skill 適用、ログ対応を確認する。費用発生と社内ポリシーへの適合を事前確認する。
- 失敗、承認、ロールバック、重複配送、部分成功を正常系と同じ受入対象とする。

## 12. 実装順序と未決事項

### 12.1 実装順序案

1. 技術検証: CLI の生成・resume・モデル変更、skill 適用、ログ形式、強制終了の識別と再開許可、MCP 接続方式。
2. 永続実行基盤: DB、WorkOrder / WorkProcess / Task / WorkLog / Run / Operation、Checkpoint / TaskAssignmentEvent、非同期 Runner、排他、冪等性、監査。
3. 社員運用 Web: AI 社員と初回 Session の一体作成、組織一覧・組織図・権限、業務指示・結果報告、Task・業務日誌の閲覧、モデル料金、ガイドブック、会話・1on1。
4. 管理自動化: cron、継続業務の実行回、基本業務、MCP 委任、inbox / outbox、cooldown、再接続・復旧。
5. 受入: AT-01〜AT-20、AT-22〜AT-30、および採用した補償操作に対する AT-21 を実行し、残課題を確認する。

FR-01〜FR-18 を現行の要件対象として扱い、削減する場合は利用者に明示する。実装順序は優先度による要件削除を意味しない。
